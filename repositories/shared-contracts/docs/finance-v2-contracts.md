# Finance protocol 2.0.0 proposal

Package 0.6.0 introduces nine exact 2.0.0 finance schemas while retaining their advertised 1.0.0 schema and fixture bytes. The proposal implements the [finance captain decision](https://github.com/Jevelopers-neatHack-2026/cost-intelligence/issues/13#issuecomment-6104393313) and locally repairs FC-001..004. Producer/consumer review and immutable adoption are still pending. The [impact record](../compatibility/finance-v2-impact.json) records the breaking migration.

The affected names are BudgetReservation, ReserveRequest/Result, SettleRequest/Result, ReleaseRequest/Result and QueryRequest/Result. Root TypeScript names are unions of every supported version; version-suffixed types and ContractVersionMap preserve exact decoding. Use the v2-only helpers for the new guarantees:

```ts
import { parseContractVersion, checkFinanceReservation } from '@jevelopers/shared-contracts';
import type { FinanceContext } from '@jevelopers/shared-contracts';
export function checkCurrent(json: string, serverContext: FinanceContext) {
  const parsed = parseContractVersion('BudgetReservation', '2.0.0', json);
  return parsed.ok ? checkFinanceReservation(parsed.value, serverContext) : parsed;
}
```

The serverContext comes from independently authenticated Finance/application records. It never comes from submitted payload fields. The package performs comparisons and exact arithmetic only; it does not authenticate a caller, issue permission, atomically reserve/release funds, post a ledger delta, or contact a provider.

| Field / record | Meaning |
| --- | --- |
| finance_protocol_version | Exact finance semantic profile 2.0.0; the common privacy/version policy remains 1.0.0 |
| held, requested_capacity, grant_request_ref, grant_revision | Immutable original authorized capacity, requested conservative cap and exact initial request binding |
| consumed, consumption_basis | Effective cumulative observed cost; actual cost can exceed authorization |
| overrun, exception_refs | Exact excess over original authorization and independently bound Finance exception evidence |
| retained_exposure, released_capacity, unreported_exposure | Conserved unused authorized amount retained until finality, explicitly released on finality, and separate unknown future exposure |
| dispatch_cap, dispatch_acknowledgement_ref | Monetary ceiling independent of actual costs; partial grant acknowledgement may report a cap but never authorizes partial work; terminal/overrun records allow no additional dispatch |
| settlement_intent | none on initial snapshots; explicit partial or final on settlement |
| consumption_kind, consumption_evidence_ref, correction_ref | Regular observations, late charges or append-only corrections with immutable evidence |
| ReserveRequest.pricing_basis, partial_grant | Bounded conservative pricing and explicit opt-in for a distinct partial outcome; unknown/unbounded pricing cannot auto-authorize |
| Result.request_ref | Exact request identity/version/hash; result economics must match the independently supplied command |

Money uses exact nonnegative decimal strings, currency and explicit scale. No floating-point posting or clamping occurs. Held 1.00 and observed 1.10 records all 1.10, overrun 0.10 and zero further dispatch; held remains 1.00. Final observed 0.60 records a 0.40 release and zero retained exposure. Partial observed 0.60 retains 0.40 with unknown future exposure. These are semantic representation checks; Finance alone posts the effective replacement/delta and releases capacity atomically.

Full grants equal the exact requested conservative amount. A smaller response cannot silently call itself full; excess authorization also fails. A partial grant requires allow_with_acknowledgement, a partially_granted outcome, an exact smaller held cap and zero initial dispatch. FinanceContext.dispatch_acknowledgement independently binds scope/modes, reservation, grant revision, request reference, monetary cap, reference, current status and expiry. This permits truthful capacity reporting and preserves the hold; it does not bind an actual replan or allowed work. Every otherwise valid partial grant returns UNSUPPORTED_CASE at /decision from checkFinanceDispatch, including cap-acknowledged grants. Until a reviewed versioned allowed-work/replan interface exists, partial dispatch is intentionally unsupported. No asserted plan ID or inferred scope fills that gap. Revoked/expired acknowledgement checks remain enforced. Full safe dispatch remains supported; already-running/finished attempts, unknown usage, terminal records and excessive requested amounts still reject. This is not a dispatch service or an atomic check-and-spend primitive.

Ordinary settlements are cumulative. Success preserves exact command amounts, intent, evidence and prior revision. Each advancing snapshot uses the next revision and a distinct event ID. Standalone reservation validation permits exact equal-revision snapshot redelivery; a successful mutating settle/release result always requires the successor revision relative to its original pre-command snapshot, including cached replay. An altered idempotent command conflicts. Increased cost cannot reuse the same observation reference. Finality needs independently supplied complete usage and a resolved execution state; timeout, lease expiry or cancellation request is insufficient.

Partial consumption can report authenticated known subtotal while execution/usage remains incomplete, without releasing unused or uncertain exposure. A currently unsafe scoped settle/release request can receive held_for_reconciliation. Its request shape/identity is checked without executing transition eligibility; held/consumed/overrun/evidence/retained/released exposure remain conserved and final settlement stays null. Actual release/final settlement still fails during in-flight/uncertain execution. Conserved partial holds use prior_observation, not the proposed new command's observations.

The reusable reservation boundary applies terminal finality to direct snapshots, current/prior context, duplicate responses and every nested result route. Released/expired snapshots cannot erase exposure when execution is finished but usage is incomplete or unknown, even if the lease expired. Complete usage with resolved execution remains valid. The only incomplete/unknown-usage release exception is independently fenced not_dispatched execution with zero consumed amount and an exact scoped FinanceResolution matching resolution_ref; a missing, changed or differently scoped resolution rejects. A resolution saying merely finished supplies no missing usage proof. Release command eligibility enforces the same fence.

Successful QueryResult dispositions must match the independently bound current reservation: held/none reports its full or partial grant decision; held/partial reports partially_consumed; final consumed reports consumed; released/expired report their matching lifecycle; uncertain_in_flight reports held_for_reconciliation. All existing economic and evidence invariants still apply. Duplicate queries bind the current snapshot and the prior truthful disposition. Denied/unknown/unavailable outcomes remain representable with their required error/retained-snapshot rules and mandatory independent scope, mode and identity checks.

Every successful duplicate also validates the effective original cached outcome. previous_command must equal the exact independently bound request, and previous_result must be the original successful result with every field matching the outward duplicate except disposition. A cached duplicate or failure cannot establish that outcome. Settle duplicates bind cumulative consumed amount, partial/final intent, consumption kind, usage/correction/exception evidence and resolution to the command and independent consumption observation. Reserve and Release duplicates bind their own grant/release decisions, amounts and intent; queries retain the current-snapshot/disposition checks. Every family binds independent execution_state and usage_completeness before success. A terminal snapshot claiming complete usage cannot conceal independently unknown/incomplete usage.

When live prior state has advanced, command_prior supplies the original pre-command reservation for replay validation. A cached Reserve grant has no pre-grant reservation. These checks validate recorded facts and the original state relationship; they perform no financial transition or execution and do not renew command eligibility after lease expiry. Historical dispatch-cap facts do not authorize another dispatch. A conserved held_for_reconciliation outcome retains the original hold and uses prior_observation for known consumption, even when the attempted command proposed a different amount. Independently fenced zero-cost not_dispatched releases, complete finality, partial consumption, overrun, late charges and authorized corrections remain supported. The 0.8.1 package records this unaccepted semantic safety narrowing without rewriting any retained 1.0.0/2.0.0 schema or fixture encoding.

A successful settle/release command must name the revision of an independently supplied original pre-command snapshot. Release starts from a granted, nonclosed, zero-consumed state; ordinary settlement cannot start from consumed, released or expired state. Closed-state settlement retains the final late-charge/correction rules. Cached post-state equality cannot supply original pre-state facts. command_prior, cached previous_result and live prior have distinct roles; when command_prior is omitted, prior must actually be the original pre-command snapshot. These requirements apply to ordinary results and duplicates, independently of present execution eligibility. Package 0.8.2 narrows helper acceptance without changing retained wire encodings.

The adapter must authenticate and retain the original command, pre-state, cached success and historical acceptance evidence. FinanceContext has no historical acceptance timestamp or separate historical execution, usage, acknowledgement or authority-status interface. Cache equality and the current clock therefore do not prove time-dependent eligibility at original acceptance. The helper checks the supplied original state relationship and independent evidence, permits historical lease-expired replay without reexecution, and renews no authority. Replays whose independent evidence expectations have themselves changed require a separately specified historical consumer interface; no authenticated history receipt is inferred here.

A late charge after finality requires a new evidence-linked append-only revision and leaves old records and original authorization unchanged. An ordinary cumulative decrease fails. A decrease through consumption_kind=correction additionally needs separately supplied CorrectionAuthority: authorized current status, same scope/modes/currency/reservation/billable attempt, exact prior revision and byte hash, from/to amounts and matching correction reference. Revoked/missing/wrong-prior authority fails. Finance performs the accounting adjustment; the old reservation cannot dispatch again.

Environment and billing_mode are mandatory independent v2 context expectations. Every supplied initial request, command, prior/current snapshot and prior result is checked against them, including denied/unknown/unavailable outcomes. Nested output modes cannot silently switch simulated/test records into real/live authority. Context currency is equally bound.

DecisionPort v1 compares request, result and receipt modes with independently supplied expectations and requires finance_context.current_reservation: a validated v2 Finance record and context. Its v1 budget field is only an exact full-grant projection: identities, revision, modes, held/consumed amounts, authority and expiry must match the v2 record. Dispatch additionally runs checkFinanceDispatch before the callback. A legacy grant alone, a contradictory projection, an unacknowledged partial grant or a direct v2 record in the v1 projection slot cannot dispatch. No automatic wire conversion or caller projection grants authority; real Finance/consumer adapter review remains pending.

The old 1.0.0 wire decoder remains available, but every current operational finance helper rejects that semantic profile with UNSUPPORTED_VERSION at /schema_version. Old behavior is executable only through the internal historical fixture adapter, marked historical_finance_characterization with operational_authority=false in fixture records; it is absent from operational package exports. It supplies no authority or safety guarantee. All sixteen old counterexamples are retained as historical evidence and also independently reject through current operational entry points. Original negative fixtures were not inverted or deleted. No earlier accepted major is fabricated.

```sh
npm run contracts:check -- --contract BudgetReservation@1.0.0
npm run contracts:fixtures -- --contract BudgetReservation@1.0.0
npm run contracts:check -- --contract BudgetReservation@2.0.0
npm run contracts:fixtures -- --contract BudgetReservation@2.0.0
npm run contracts:compat -- --contract SettleResult@2.0.0
npm run build
npm test
npm run test:installed
```

The catalog and fixture manifest index all 54 supported contract/version pairs across 45 names. The compatibility matrix executes current/current, retained-old/current and current/old-rejection cases using actual exact-version validators. Unknown versions reject. Old schema/fixture SHA histories remain pinned at the 0.5.0 checkpoint. Real consumers must review the impact, pin the new package/source/schema/fixture bytes and return actual exact-revision results and acknowledgements; rollback retains the old immutable archive and encoding with its documented limits.

QueryRequest/Result still concern one reservation. FinancialSummary is a projection, not a reporting/query/export API. Reporting GAP-001 stays in [proposal intake](../compatibility/proposal-intake.json). The [fresh finance delta](../compatibility/finance-delta-findings.json) records candidate FC-003/004 invariant repairs and GAP-002 conservative dispatch refusal, pending fresh full independent and finance-owner review. Allowed-work/replanning remains unsupported and downstream. Existing 1.0.0/2.0.0 schema and fixture bytes are preserved. No full finance conformance, dependency adoption or release acceptance is claimed.
