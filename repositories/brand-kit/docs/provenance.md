## Scope and core policy

These are fixed in `tools/check_provenance.py`; editing the register cannot narrow or switch them off.

- **Scope** is always `logo/`, `fonts/`, `references/`, `tokens/`, `docs/assets/`. A register whose `scope_prefixes` omits any of them fails; extra prefixes may be added. Every tracked file in the union needs exactly one record.
- **Required core** is any file under `logo/`, `fonts/` or `tokens/`, except `.txt`/`.md` licence-notice texts. The register's `core` flag must equal this derivation (a mismatch fails the structural check), and production independently blocks on cleared rights and approval for every required-core path, whatever its classification or flag. Reclassifying a logo as `internal` or `reference-unknown` does not remove the block.
- **Optional, honestly non-core:** README banners (`docs/assets/`), reference images (`references/`) and font licence texts. They are not core, but they are still excluded from release unless every eligibility rule holds; references are excluded outright (`reference-unknown`, never first-party from appearance or location), internal and third-party items likewise.
- Fonts are core for the rights question but source-only for export: the font binaries can never be allowlisted.

## Boundaries (BK-06.4)

- **event-intelligence owns** discovered customer, event, organizer and venue assets, candidate collection and rights/permission evaluation ([OWNERSHIP](architecture/OWNERSHIP.md)). This repository stores none of those. A discovered third-party candidate is never added to `logo/ fonts/ references/ tokens/`; it stays a reference by identifier in its owner's system.
- **Creative and production owners** enforce what enters a production bundle. This validator checks only this repository's first-party allowlist; it does not enforce another repository's bundle.
- **Brand-kit owns** its approved product identity and may document a boundary or a stable contract reference, not hold other parties' assets.

## Safe evidence references (BK-06.5)

Evidence and approval fields hold references only, in one of three forms: a tracked repository path (optionally `#anchor`), a plain public `https://` URL (no credentials, no query string), or `restricted:<opaque-id>` meaning the evidence is held by a named maintainer outside this public repository. Never put contracts, customer or account details, personal email addresses or credentials here. The validator rejects secret-like strings and email addresses and does not echo them.

Review of this change for secrets and personal data, 2026-10-12, limited scope: `gitleaks 8.30.1` (locally installed; nothing installed or called out) over git history (19 commits) and over the working tree reported **no leaks**. The register and allowlist were also scanned by the validator's own patterns. Not covered: the scanner finds known secret shapes only, not private contracts or customer details in prose; GitHub issue and PR text and bundled binaries were not scanned (image and font bytes were not inspected). Commit metadata carries two author email addresses, which are public git metadata and are not copied into any file here. This is not a claim that the repository is free of sensitive data.

## Updating the register

Hash drift is expected when other changes touch these files (BK-03A changed `tokens/`; the register was refreshed at `28e64dd`). Regenerate token outputs only with `make build-tokens`, and confirm `make check-tokens` and `make check-provenance-register` both pass afterwards. `make check-provenance-register` then fails with the actual hash. Refresh by hand with `--print-hashes`, update `sha256`, `size_bytes` and `source_revision`, and record why. A changed file invalidates any earlier approval for the old hash. A new file under the scope fails coverage until it gets a record. Replace `UNKNOWN` only with a reference to real evidence; never write an approval on someone's behalf. To make something exportable: resolve rights, record approval evidence and reviewer in the register, then add the exact path and hash to the allowlist in a reviewed change, per the [governance](brand-governance.md) decision process.
