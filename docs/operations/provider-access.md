# Provider access preflight

CE-A01 defines a fixed, eight-cell access matrix for the later creative smoke. It is a prerequisite report, not a blanket billing grant or release-acceptance result. Every required cell remains in the denominator, and `acceptance_allowed` is always `false`; a successful mock run reports `simulated`, never `verified`.

The plan carries explicit target and configuration pins. It cannot carry or establish credentials, owner approval, operation permission, quota, Finance authority, or a reservation. Those decisions come from injected adapters in the trusted host composition. A serialized plan or a port object loaded from user-controlled JSON is not a trusted integration. The `evidence_mode` field labels a source; it is not authentication by itself.

An unresolved target stays blocked. The runner does not substitute a convenient model, use a moving alias, or treat model listing as permission. EVAL-03 remains Product and frontend owned; FIN-10 and SPN-01 remain Finance and reliability owned. This preflight records the Creative and fulfillment contribution without changing those roles.

## Trusted capability and Finance ports

Before a billable cell can request a reservation, the host supplies a trusted `AccessCapabilityVerifierPort`. Its decision must bind the authenticated tenant, project, and budget scope; provider account and project; cell and owner; exact service, endpoint, model, SDK/runtime and configuration digest; operation; and the approved deadline. It returns separate operation-permission and quota states, evidence hashes and pinned independent-review references, owner role, protocol pin, check time, and expiry. Evidence must be fresh (at most five minutes old) and valid through the exact operation deadline. The verifier is called again at the dispatch boundary after the reservation is established. If capability or authorization is denied, unknown, stale, expired, or revoked, no provider transport starts. A hold already established remains for reconciliation when the result is uncertain.

The capability verifier is deliberately distinct from the provider metadata adapter, pin verifier, authorization verifier, and Finance verifier:

1. The provider adapter can check non-billable account authentication and model listing. The built-in Images adapter reports permission and quota as unknown because the model-list endpoint does not establish either for an image operation.
2. The capability verifier must independently confirm current eligibility and quota for the exact operation and target. A model-list result, configuration pin, or later billing grant cannot replace it.
3. The authorization verifier must authenticate an external grant for the same tenant/project/budget, provider account/project, full target and operation, logical operation and billable-attempt IDs, exact cap/currency, deadline, and stop conditions. It is revalidated both at dispatch entry and after the metering authority acknowledges the single transport identity.
4. The Finance reservation verifier must confirm the actual reservation and active lease against the same grant/evidence, attempt, full target, cap, and currency. The accepted Finance protocol must enforce one-use authorization, aggregate caps, and lease binding.
5. The existing C03 metering consumer records distinct logical-operation, billable-attempt, transport, provider-request, and usage-observation identities. The provider adapter records its single transport, awaits Finance acknowledgement, revalidates the current Finance lease, capability, and grant, then performs a synchronous cancellation/deadline/expiry/freshness check immediately before network I/O. It must not retry.

Those independent verifications are sequential reads. This proposal does not claim atomic cross-authority revocation protection: a provider, grant issuer, and Finance service can change state between their separate responses. A live integration needs each external owner to define the binding and dispatch linearization semantics for its one-use grant and lease. If any post-acknowledgement check is denied, stale, unavailable, expired, revoked, or cancelled, the adapter sends no Images POST and C03 retains the acknowledged attempt for reconciliation.

These are injected interfaces, not a claim that Creative owns or implements the provider, capability, authorization, or Finance authorities. The current external agreement and accepted account/owner evidence are missing. The test fixture is explicitly fake and only exercises boundary behavior; it cannot satisfy a live cell or prove account quality.

## Direct OpenAI Images adapter

The built-in generation/edit adapter uses one native `fetch` request to the explicit Images endpoint. It is not the official OpenAI SDK and does not call the Responses API. The target pin labels this client as `native-fetch` and checks its version against the actual `process.versions.node` value. The adapter does not read environment variables, choose a model, follow redirects, retry, or log authorization headers.

Current official references list the dated Sunburst snapshot as an Images model candidate and document separate generation and edit endpoints. They also describe `OpenAI-Organization` and `OpenAI-Project` request headers, which scope usage to the named IDs. The credential resolver must independently bind the token, provider routing IDs, exact target, and—on a billable operation—the grant reference before the adapter sends either a read-only model-list request or a paid request. This documentation does not establish eligibility for the configured account. See the [Images API guide](https://developers.openai.com/api/docs/guides/images-vision), [generation endpoint reference](https://developers.openai.com/api/reference/resources/images/methods/generate), [edit endpoint reference](https://developers.openai.com/api/reference/resources/images/methods/edit), and [API authentication and project headers](https://developers.openai.com/api/reference/overview).

Edit input must match the pinned asset digest and pass bounded PNG structure, checksum, and decompressed-scanline checks before the credential resolver is called. Indexed-color PNGs are explicitly rejected because this bounded decoder does not validate palette indexes. A successful output requires a supported, decoded PNG with the exact pinned 1024×1024 dimensions. The report contains its digest and dimensions, not image bytes. Raw provider request IDs are represented only by a SHA-256 surrogate. Provider JSON and image bytes have size limits. When token usage includes input/output text and image detail counts, the adapter preserves each as an `included_subset` of its input/output parent; top-level input/output are themselves subsets of total. Missing or malformed reported usage dimensions remain explicit as partial/unknown, are never priced locally, and keep the C03 hold in reconciliation.

The documented model candidate is not a selected owner-approved target. The fixture's prompt, account IDs, evidence, Finance authority, reservation, and provider responses are test-only. No provider call, account inspection, JEV request, or Neatlogs write/read was made for this implementation.

## OpenRouter Images adapter

`createOpenRouterImagesProvider` is a second image provider path, selected by the host, not a replacement for the direct adapter. See [OpenRouter Images adapter](../providers/openrouter-images.md) for the sourced API facts, the profile, and the unsupported list.

| Capability | Implemented offline | Verified account access |
| --- | --- | --- |
| Generation (`POST https://openrouter.ai/api/v1/images`, no references) | Yes: intercepted-transport wire contract, capability and authority fences, output and usage validation, API/C03/CE08/CE11 integration. | Owner-authorized live smoke on #37 (2026-10-11, one request), recorded with operator-attested ports. This is not trusted-owner-service evidence and the CE-A01 preflight has not verified it. |
| Reference-guided edit (parent first, then manifest references as data URLs; separate capability) | Yes, with the same offline coverage. It is image-to-image guided by references: no mask, and no documented parent preservation. | Owner-authorized live smoke on #37 (2026-10-11, one request with one reference), same attestation limits. Edit entitlement and the per-model reference maximum stay separate from generation. |
| Parentless concepts (authorized references only) | Yes, through the edit capability. | **No.** No concept-batch smoke was run. |
| Masked or inpainting edit | Rejected before credential resolution. Direct OpenAI remains the only masked route (CE-07). | Not applicable. |

The host variable `CREATIVE_ENGINE_OPENROUTER_API_KEY` is a placeholder for the key the trusted host injects through the credential port. The adapter reads no environment, and there is no fallback to `OPENAI_*`, `OPENROUTER_API_KEY` or the customer app's `TICKETSTUB_ART_OPENROUTER_API_KEY`; reusing those requires an explicit owner decision (G1). Model discovery (`GET /api/v1/images/models`) is a catalog only and cannot satisfy the capability verifier. Account-wide provider settings merge with request routing and must be checked outside this repository (G2). OpenRouter's reported `cost` is retained as provider-reported and unsettled (G4); a transport-started attempt whose outcome is not observed keeps its C03 hold.

The live gate is fail closed: `make check TARGET=openrouter-image-adapter MODE=live` exits 2, reports `provider_dispatches: 0` and `provider_credentials_read: false`, and lists the open gates G1-G6.

### OpenRouter targets in the CE-A01 matrix

The fixed eight-cell denominator is unchanged. The `image_generation` and `image_edit` cells can each carry either the direct OpenAI target or an OpenRouter target, and they stay separate cells with independent evidence: an OpenRouter generation pin, observation, capability decision, grant and reservation never count toward the edit cell, and the reverse. An OpenRouter target is validated by `validateOpenRouterImageTarget` and must pin:

- `service: "openrouter"` and `endpoint: "https://openrouter.ai/api/v1/images"` (the same endpoint for both cells);
- an explicit `author/slug` model id, with no default and no alias;
- the actual `native-fetch` Node runtime version;
- configuration keys `prompt_template_ref`, `prompt_template_sha256`, `provider_tag` (the single pinned provider, sent with `allow_fallbacks: false`), and `profile_sha256` (the owner-approved digest of the exact adapter profile). The edit cell adds `asset_ref`, `asset_sha256` and an image `asset_mime`; the generation cell may not carry them.
- optionally `catalog_entry_sha256`, the expected hash of the live catalog entry (`provider_tag`, `supported_parameters`, `pricing`, canonicalized as in the evidence digest). It is part of the configuration, so the target's `configuration_sha256` binds it.

`model_listing: "listed"` from the OpenRouter adapter means only that the catalog offers the pinned `provider_tag` for the pinned model. It is not a profile match: parameters, capabilities and prices may differ from what the owner approved. When `catalog_entry_sha256` is pinned and the live entry hashes differently (or cannot be hashed), the adapter reports `unknown` (the runner then blocks the cell as `model_unknown`) and the evidence digest records `listing_reason: "catalog_entry_mismatch"`. A missing tag stays `not_listed`.

The metering `operation_kind` of the cells is still `image_generation` and `image_edit`. The runtime adapter's own dispatch binding labels OpenRouter edits `image_reference_edit` because they are reference-guided and unmasked; a host that composes the billable dispatch maps between the two.

`createOpenRouterImagesAdapter` is the OpenRouter equivalent of the direct adapter's non-billable account check. A trusted host composes it with a live `credentialPort` and an explicit `fetchImpl` (there is no global default and no environment read). Its `inspect` makes at most two reads: `GET https://openrouter.ai/api/v1/key` with the resolved bearer token for authentication (balance, limit and usage fields are not retained), and the public `GET https://openrouter.ai/api/v1/images/models/{author}/{slug}/endpoints` without any credential, to see whether the pinned `provider_tag` is offered. As everywhere else, a valid key and a catalog entry are not entitlement: the adapter always reports `operation_permission` and `quota` as `unknown`, and the runner discards those fields in favor of the independent capability verifier. The adapter has no built-in billable request; `prepare` and `dispatch` exist only when the host passes a trusted `dispatchPort`, and each re-validates the OpenRouter pin first. `prepare` is at least as strict as the direct adapter's: it requires the authorized `grant_ref` and an unexpired `deadline_at`, resolves the credential through the credential port with purpose `authorized_billable_operation` bound to the grant, account, project and exact target (the binding must echo the same `grant_ref`), and requires the credential's `expires_at` to be at or after the operation deadline. Only then is the host `prepare` called, with the bound `credential`. `dispatch` accepts only the prepared value this adapter minted for the same cell, target, grant and deadline, refuses once the deadline has passed, consumes the prepared value on use (a second dispatch with the same value is refused before the host port), also requires the same account and project scope, and calls the host port with the credential, the host's prepared value and an abort `signal` that combines the runner's cancellation signal (`metering.signal`) with a timeout capped by the deadline (at most 120 s). Every clock read must be finite; a clock that stops returning a finite number after construction makes `inspect`, `prepare` and `dispatch` refuse (`adapter_unavailable`) before any credential, fetch or host call, except that a fault while the credential is being resolved (its expiry comparison reads the clock) surfaces as `credential_unavailable`; either way it fails closed and the host `prepare` is not called. `prepare` also re-reads the clock after the credential await and refuses with `preflight_deadline_passed` if the deadline has passed before it calls the host `prepare`; the prepared value stores a copy of the account and project references, not the caller's scope object. Remaining host obligations: verify, before dispatch, that the rendered prompt hashes to `prompt_template_sha256` and, for an edit, that the asset bytes hash to `asset_sha256` with media type `asset_mime` (the direct OpenAI preflight adapter does this itself through its prompt and asset ports; this adapter has no such ports and delegates it), send exactly one request with only that credential, enforce the pinned provider tag and no fallbacks, honor the `signal`, drive the metering fence (`recordTransportAttempt`, `authorizeTransport`, `assertTransportReady`) before transport, never log or return the token, and return evidence that decodes to the pinned 1024x1024 PNG.

The offline tests exercise this adapter only with intercepted fetch. The mock run adds four synthetic scenarios (OpenAI and OpenRouter, generation and edit); in the two OpenRouter scenarios the real `createOpenRouterImagesAdapter` performs its two reads against an in-memory `fetchImpl` and a synthetic credential port (nothing leaves the process), and the evidence lists the simulated result of each image cell per provider under `test_fixture_only.image_cell_targets`. The live gate groups the per-provider permission and quota evidence of each image cell as one `one_of:` requirement, because either target satisfies the cell. The run remains `simulated` with `acceptance_allowed: false`; the live gate still exits 2 with zero dispatches and no credential read. A successful live image result must still decode to the exact 1024x1024 PNG recorded in the preflight evidence, so an OpenRouter profile must pin dimensions that produce it.

Owner-authorized live smoke evidence exists on issue #37 (2026-10-11: one generation and one reference-guided edit, recorded with operator-attested capability, authorization and Finance ports). That evidence exercised the adapter's wire contract, entitlement and output handling, not this preflight. The preflight itself still requires trusted host adapters (credential, capability, authorization, Finance reservation and, for a paid cell, dispatch) that this repository does not install.

## Run and verify

The public ESM and strict type entrypoint is `creative-engine/preflight`. The deterministic checks are:

```sh
make check TARGET=access-preflight MODE=mock
make check TARGET=access-preflight MODE=live
```

The mock command runs generation and edit for both provider targets through synthetic ports, keeps the other six required cells visible as blocked, and writes sanitized evidence to `build/access-preflight-evidence.json`. Its report remains `simulated_or_pending`, with `acceptance_allowed: false`. The live command writes `build/access-preflight-live-gate.json`, emits the blocked eight-cell gate as JSON, and exits 2 while trusted capability, authorization, Finance reservation, and owner adapters are absent. It performs zero provider dispatches and reads no credentials. It never loads adapter claims or grants from user-editable JSON. The exported `runAccessPreflight` function is executable with real trusted adapters supplied by a host composition; this repository does not contain or install that composition. `make acceptance TARGET=access-preflight` and `make acceptance TARGET=all` keep CE-A01 pending until the external evidence and actual authorized access work are available.

Standalone checks for these source files are:

```sh
node --test tests/preflight/*.test.mjs
node --check src/preflight/access.mjs
node --check src/preflight/openai-images.mjs
node --check src/preflight/openrouter-images.mjs
```

The strict NodeNext consumer check uses TypeScript 5.9 with `strict` and `skipLibCheck: false`. Tests exercise fixed denominators, individual cell separation, missing/denied/unknown capability, scope/deadline/freshness mismatches, stale grant revalidation, denied and mismatched reservations, uncertain release/usage holds, one-transport limits, privacy-safe diagnostics, account/project-bound credential routing, PNG validation, and the absence of retry or fallback behavior. Live provider, Finance, JEV, and Neatlogs execution remains pending their respective owner agreements and exact authorization.
