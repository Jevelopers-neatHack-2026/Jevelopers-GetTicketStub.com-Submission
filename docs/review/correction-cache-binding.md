# Private correction-history and scoped-cache binding

This document describes the EI-local composition seam in `src/review/history/cache-binding.mjs`. It binds a private scoped-cache profile to one immutable correction-history version so a supported composed read cannot return the old profile after a correction or source refresh commits. The module is an internal implementation seam; it adds no public route, package export, authentication contract, Finance allocation, or Creative-use approval.

## Exact binding

A binding is issued only after the composed facade has authenticated both store scopes and confirmed the same tenant and actor. The history database stores the binding and matching downstream reference as authenticated ciphertext. Its payload ties together the event ID, current history version ID and content hash, deterministic projection hash, cache-issued profile reference, private cache scope, cache entry version, identity, all version pins, source content hash, and the minimum history/cache expiry. The cache entry carries a keyed binding digest and the same history coordinates. Opaque profile references and correction references remain distinct identifiers; neither can be substituted for the other.

On read, the facade first resolves the current history head and finds exactly one unexpired binding whose event, version, content hash, projection, identity, pins, and source hash match the request. It then checks the cache entry, latest observation, freshness, permission references, and cache version. The required synchronous host guard, with action `private_profile.read`, is the last host decision: it binds the current request principal and permission state to the exact tenant, actor, event, and trusted `nowMs`. Its permit is a plain own-data record with exact scope/action fields; a missing guard, promise, proxy, accessor, malformed permit, denial, or scope mismatch fails closed. The history fence and cache transaction then validate the exact current head, binding, entry, observation, expiry, and permission deadline without another host callback or await before facts are returned.

## Correction and recovery ordering

The history database is the durable barrier. A bind or revision operation first commits its immutable operation fingerprint, operation ID, base version/hash, monotone fence, and pending phase. While that phase is incomplete, composed history reads and cache reads are blocked. A bind writes the cache profile with the binding digest, then records the encrypted binding and reference in history, and only then completes the operation.

Before a bind barrier is written, the facade validates the exact current history head and deterministic profile projection. It applies the cache's actual candidate and support-reference limits to the full projection and rejects a projection that cannot be stored; it never truncates source claims or alternatives to make them fit. The prepared plan is tied to the captured base version, content hash, and reference digest, then revalidated before the barrier transaction. A concurrent history change fails before creating a new binding operation. Corrections and source refreshes likewise materialize the complete next immutable snapshot, including all local invalidations, against the captured base before committing their barrier. History aggregate limits and sealed-version byte limits are checked on that exact snapshot; a deterministic over-limit input leaves the old history readable and creates no pending operation.

Composed operation rows now carry a durable receipt with the exact base version/hash, operation fence and phase, and target version/hash. A schema migration fills a missing receipt only when the current singleton state and available history head prove that exact operation and fence. Older completed rows that cannot be reconstructed from current state remain unproven and fail closed on replay; migration does not invent a fence or permit replay of an unknown historical operation. An exact completed correction or source-refresh replay may be returned after a later bind of the same target head, provided the durable receipt, current head, actor, idempotency fingerprint, expiry, and final read guard still match.

Before the bind barrier, the cache participant rechecks its scope context, then resolves the private references, lineage, invalidation consumers, and write-specific encryption keys once. It checks the full event envelope for each consumer with the production sealer, including the maximum retry attempt, escaped and multibyte consumer identifiers, key identifiers, and encryption overhead. It also verifies total payload bytes and both correction and general outbox-slot reservations. The resulting process-local, one-shot preflight is bound to the exact input and history coordinates, consumed by the cache write, and discarded with its key buffers cleared on every exit. The bound write does not call those host resolvers again after the durable barrier. This moves deterministic capacity and envelope failures ahead of the durable barrier. A later concurrent capacity change or external failure can still leave the durable operation pending; the protocol preserves that exact barrier for retry rather than clearing uncertain work.

A correction or `refreshSources` commits the new history version and exact operation target while leaving the barrier active. For each still-live binding, the facade acquires the history writer transaction first, then the cache writer transaction. The cache commit checks the live history operation ID/fence/phase in the history transaction and atomically marks only the exact cache version ineligible, converts its reserved capacity into encrypted outbox events, and writes an idempotency receipt. The history transaction is then committed. A later short history transaction marks the binding reconciled. The final history transaction clears the barrier after every still-live target binding has an exact receipt and target version/hash. Expired mappings are pruned under the history writer before enumeration; they no longer target a usable cache profile and do not require a second cache event. If expiry races a correction after mapping enumeration, the durable barrier stays active until exact retry prunes the expired mapping and completes the same operation. The ordinary history reference remains and still receives its exact local invalidation for the revision.

After cache invalidation and operation completion, the facade does not return the earlier history snapshot. It re-reads the exact completed operation and checks the head, target hash, completion fence, and receipt at the final `private_profile.read` boundary. The same check gates an idempotent replay, including a replay that followed earlier host work. A late authorization denial, expiry, or genuine abort returns no snapshot even if the history and cache effects already committed; the durable operation remains available for an exact retry, which returns that same version without duplicate cache invalidation work.

An exact bind retry authenticates the immutable history operation fingerprint and the complete cache receipt, entry, reservation, observation, and consumer rows before it decides whether this is a replay or a first cache effect. A receipt replay uses the original source observation, validation time, captured freshness TTL, absolute expiry, and recorded payload-key IDs; it does not resolve new consumers, reseal an invalidation envelope under the current key, or renew freshness. Changing an explicit TTL, expiry, observation input, identity, pins, content hash, or facts under the same idempotency key conflicts with the original operation. A changed default TTL also leaves the stored receipt unchanged. While the exact cache receipt remains before its hard expiry, an idempotent bind call may return its original bound metadata after the freshness deadline; that result contains no profile facts and does not imply that ordinary cache reads remain fresh. The composed profile read reports `stale` with no facts after the original TTL. At hard expiry the replay fails closed and never recreates the cache entry. A pending operation with no cache receipt may make its first effect only through a fresh, fully validated admission; a partial or uncertain receipt keeps its existing barrier for exact reconciliation.

These two SQLite files do not have a global atomic commit. If the process dies after the history revision commits, its durable pending barrier prevents composed reads from using the old profile. Exact retry resumes the same operation and never rebinds to a newer unrelated version. If the cache commit succeeds before history records its receipt, the cache receipt makes retry idempotent and prevents duplicate outbox events. The same-process queue and zero-timeout SQLite writer attempts use bounded asynchronous retry; no host callback or event-loop-blocking busy wait runs while a paired writer lock is held. The live operation fence is checked synchronously at the inner commit boundary, so a late continuation cannot commit after an exact retry takes over.

The guarantee covers calls through this composed facade. Independent direct calls to either standalone store, manual database edits, filesystem restoration from inconsistent snapshots, or another writer that bypasses these stores are outside the paired protocol. The history barrier and cache eligibility guard must be deployed together and persisted in their respective local databases.

## Authorization, retention, and invalidation delivery

The injected tenant, actor, authorization, key, retention, source-observation, permission, and boundary adapters are trusted host preconditions. Their presence or a successful test callback does not establish production authentication or an external approval. The former composed-read `authorizeFinalDisclosure` callback is replaced by the required synchronous `authorizeBoundary` permit, and the history store now requires its own `authorizeBoundary` guard as well. Each guard returns the exact tenant, actor, event, action, field, and trusted `nowMs`; missing, denied, asynchronous, malformed, or mismatched permits fail closed. The cache's `authorizeBoundary` option remains optional for standalone callers, preserving their existing authorization contract, but is required when a cache is attached as a composed private participant. No host auth callback runs inside a SQLite writer transaction, and no await or host clock callback follows the final boundary check before its protected transaction/disclosure. The persisted clock watermark uses the guard's actual sample; captured monotonic elapsed time is used separately for expiry checks at transaction start and immediately before commit. Retention uses the earlier of the cache and history deadlines. At cache expiry, one cache transaction records the existing `retention_expired` outbox event, scrubs the profile payload, and removes its encrypted correction reservation; pending delivery and acknowledgement state remains intact. History cleanup removes encrypted cache mappings at their effective expiry even while the history head and ordinary downstream reference remain live. A correction after that expiry therefore keeps the history's local reference invalidation but does not emit a redundant cache `history_version_changed` event. An expiry discovered after asynchronous key or authorization work is persisted by a separate short history cleanup transaction before the typed expiry error is returned.

The cache transaction makes a bound row locally ineligible and persists its invalidation outbox work. Local ineligibility is separate from external acknowledgement: a missing, unknown, rejected, or unverified acknowledgement stays pending and continues to block readiness. Retrying a correction does not duplicate a receipt or outbox event. This local behavior does not assert that an external consumer acted, that a permission was issued, or that a Finance usage or hold is resolved; unknown Finance usage remains unknown.

The composed TypeScript lookup result omits `profileRef` when history retention has expired. Other unavailable cache results keep the cache's existing reference field. The standalone cache result type and standalone lookup contract are unchanged.

## Evidence boundary

Tests use temporary local SQLite databases and synthetic host callbacks. Cross-process writer contention and process termination are exercised locally. These tests do not prove production identity, permission or retention adapters, external consumer delivery, live provider behavior, Finance settlement, Creative acceptance, or whole-issue closure. Those remain separate acceptance evidence.
