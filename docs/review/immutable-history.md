# Private immutable correction history

`src/review/history/store.mjs` adds an internal typed projection API for private event-fact review. It is an EI-10 P0 contribution. The store persists source assertions, customer corrections, stable review questions, immutable version links, and local downstream-reference invalidations. It does not implement the canonical `ResearchRequest` or `EventIntelligencePackage`, a customer route or UI, an external approval validator, an asset-use permission decision, or the final creative handoff. EI-10 remains required and open until its full issue gate is met.

The API uses four bounded fields: `event_name`, `event_date`, `venue`, and `event_status`. Dates must be date-only, local date-time with an IANA time zone, or an explicit UTC instant. A local date-time must exist in that zone; a spring-forward gap is rejected. A fall-back fold is retained as the supplied wall time and zone without selecting either possible instant. Explicit instants use UTC `Z`, hours 00–23, minutes and seconds 00–59, and retain their accepted fractional-second text without normalization. Missing required fields produce typed questions. Conflicting source values remain visible with their evidence references, and conflicts or later source disagreements on every supported field, including status, produce review questions. A customer answer becomes `customer_supplied`; it does not become sourced or independently verified. Initial facts accept only `sourced` or `inferred` origins, so customer values enter through the authenticated correction operation. The prior version keeps its original values and questions. The new version keeps source claims and exposes any disagreement with the customer value.

Source refresh is append-only. A refresh cannot replace the current customer value. A newly observed source claim that differs from that value creates a `SOURCE_REFRESH_REVIEW` question. A source fact input can carry only source or inferred origins; customer values enter through the correction operation. Source evidence references are bounded identifiers and hashes from the trusted producer projection. This store validates their shape, but does not resolve those references against the evidence store or claim that a hash proves source authority.

Each write compares both the current version ID and content hash while holding a SQLite `BEGIN IMMEDIATE` transaction. A successful write adds a new encrypted version, parent link, canonical content hash, idempotency record, and any reference invalidations in the same transaction. Access to each tenant database is queued within the process for the full transaction and cleanup lifetime; SQLite locking still protects competing processes. The event, actor, idempotency key, and downstream reference lookup values use tenant-keyed HMACs. History payloads and reference IDs are AES-256-GCM encrypted. After asynchronous key, retention, and reference work, the store re-resolves tenant and actor identity, reauthorizes the same action and field, and checks the persisted expiry immediately before commit. Private reads and idempotent replays perform the same final identity, permission, and expiry checks before returning data. An older version's own deadline and the latest persisted head deadline both apply to historical reads and replay, so a shorter later retention decision expires the whole history. A retry with the same scoped idempotency key and exact actor, operation, base version/hash, and value returns the committed version, including after restart. Reusing that key with different input returns a typed conflict. Competing processes from one base can commit only one version.

The explicit materiality rule is based on the visible projected facts, their source claims and evidence references, and open review questions. A change to that projection is material. Repeating the same customer value can create a new immutable revision whose material hash is unchanged. Every new revision invalidates all local downstream references tied to the exact prior version ID and hash, including on a nonmaterial revision. This prevents a reference from silently inheriting applicability. The invalidation record is descriptive local history only: an `approval_reference` is not an approval, and this module cannot authorize artwork use or validate an external authority’s signed decision.

## Trusted host preconditions

The application composition root must provide:

- `resolveTenant` and `resolveActor`, both derived from authenticated server-side request context;
- `authorize`, which checks each requested read, correction, source refresh, and reference action for that exact tenant, actor, event, and optional field;
- `resolveKey`, backed by the trusted key manager, returning fresh 32-byte keys for `correction_payload` and `correction_index`;
- `resolveRetention`, which validates an app-issued retention handle and returns a `tenant_private` expiry. The store rechecks this decision before commit and caps every revision at the previous history expiry, so a correction never extends the original retention window;
- a private local filesystem directory with an administrator-controlled parent.

The store issues an opaque process-local scope only after `resolveTenant` succeeds, then rechecks tenant and actor identity and invokes `authorize` on every operation. A caller must pass a genuine, non-proxy `AbortSignal` directly from trusted in-process code. The store rejects proxies with captured `node:util.types.isProxy` before reading cancellation state through the captured native `aborted` getter, and ignores an ordinary own-property override. A bare object with only `AbortSignal.prototype` is rejected, but on Node 22 a caller can copy the runtime's exposed symbol properties from a genuine signal onto another object and satisfy the getter; this check is not an authenticity boundary for symbol-copied objects. No client-supplied tenant, actor, role, approval, or boolean flag grants access. The trusted callbacks are preconditions, not authentication or authorization implementations supplied by this module.

SQLite runs with rollback journaling, `synchronous=FULL`, `secure_delete=ON`, tenant directories at mode `0700`, and database files at mode `0600`. The store rejects a symlink or non-regular database path. Configured limits bound the canonical plaintext snapshot (512 KiB), the serialized encrypted version envelope before insert (512 KiB), each history (200 revisions), per-history reference count (128), tenant histories (1,000 including retained expiry tombstones), and stored encrypted payload bytes (64 MiB) by default. Migration from the prior non-null version-ID schema transactionally normalizes already-expired rows and removes linked private metadata while preserving available encrypted histories. On expiry it deletes encrypted payloads, idempotency keys, references, and invalidations; only event-keyed revision/state tombstones remain, with version identifiers and parent links cleared. If an operation is denied or fails after discovering expiry, its mutation transaction rolls back and a separate expiry sweep commits cleanup. Reads return no partial history. Retention is capped at 30 days by default, or by a smaller injected policy.

The filesystem parent and its administrators remain trusted. This module does not defend against a same-user attacker racing path replacement or direct database edits, and no network-filesystem locking guarantee is claimed. The index-key resolver must remain stable for a tenant’s retained history; payload key IDs are passed back to the resolver for reads. No production key, customer data, provider call, or approval credential is embedded here.

## Local verification

Run on the pinned Node 22 runtime:

```sh
node --test tests/review/history/*.test.mjs
./node_modules/.bin/tsc --noEmit --strict --target ES2022 --module NodeNext --moduleResolution NodeNext --lib ES2022,DOM --types node --skipLibCheck false tests/review/history/types-consumer.mts
```

The local tests use synthetic tenant/actor context, test-only keys, and synthetic retention permits. They cover targeted questions, immutable correction provenance, forged and locked fields, exact idempotency and restart replay, source-refresh disagreement, material and nonmaterial invalidation, cross-process and asynchronous same-process compare-and-swap, same-key replay across store instances, queued cancellation and cleanup, process death during an open transaction, private file modes, encrypted payloads, current-head expiry during historical reads and all replay paths, cleanup after denied expired operations, active and explicitly purged legacy-schema migration, hostile array and abort-signal inputs, DST gap/fold behavior, all-field status review, and sealed-envelope size limits. They do not verify an authenticated application journey, the producer’s evidence references, external approval validity, real creative consumption, or the full EI-10 acceptance gate.
