# Privacy and canonical hashing

Canonical encoding and contract-text duplicate-member checks support at most 64 nested object/array containers. Deeper inputs return the typed RESOURCE_LIMIT validation code; direct canonicalJson/hashManifest calls throw ContractError with that code. The bound applies before recursive schema/helper use, including object inputs, and preserves exact bytes for supported values. This is a resource acceptance limit, not a change to the canonical hash domain or Unicode policy.

Candidate policy 1.0.0 uses four field classes: public (safe to release), internal (operational correlation), restricted (private/customer/source data), and secret (credentials/authentication material). Every named property, including nested arrays/objects, carries `x-classification`. Missing classification blocks the schema audit. Domain leaves own their classifications; `--policy-only` checks the taxonomy and projection policy without claiming domain coverage.

Identifiers are internal or restricted unless a separate opaque public evidence ID was deliberately assigned. Source URLs/text, prompts, customer input, asset locations, approval actors, provider request IDs, destinations and diagnostics are excluded from public evidence. Credentials, auth headers, signed URL/query tokens and private locators never appear in EvidenceProjection. `projectEvidence` copies only the explicit public allowlist, including individual component fields. It strips all unknown fields recursively by constructing that small output and rejects unsafe values in allowed fields. Its inputs must be synthetic or supplied by a trusted sanitizing adapter; it does not establish the provenance or authenticity of claims.

The public projection contains no arbitrary messages, URLs, tenant IDs or artifact digests. Plain hashes of low-entropy sensitive data can reveal the data and are forbidden in public evidence. Where private correlation is necessary, the downstream owner uses tenant-scoped keyed pseudonyms with separate key custody, access and rotation. This package stores no keys and never promotes private stable hashes into public evidence.

`canonicalJson` implements jevelopers-json-v1: plain JSON objects only, UTF-16 lexicographic object-key order, original array order, no whitespace, JSON string escaping, well-formed Unicode preserved without normalization. Finite IEEE754 fractional numbers support scores, probabilities and controls; their deterministic spelling is ECMAScript JSON.stringify (including exponent form where applicable). Integers must be safe integers; -0 encodes as 0. Count/revision schemas must additionally enforce integer type and explicit safe bounds. Exact monetary decimal amounts remain strings, preserving every digit without floating-point coercion. Undefined, symbols, functions, bigint, dates, class instances, accessors, non-enumerable properties, sparse arrays, cycles, unsafe integers/nonfinite numbers and lone surrogates are rejected. UTC strings are validated by their schemas and never reformatted. This intentionally restricted algorithm is not a claim of complete RFC8785 support.

`hashBytes` computes SHA-256 over exact supplied Uint8Array bytes. `hashManifest` computes SHA-256 over UTF-8 canonical JSON. Both return `sha256:` followed by 64 lowercase hex digits. A manifest must exclude its own digest field before hashing; byte and manifest digests are distinct scopes and any changed bound content requires a new digest/version and downstream approval where applicable. Hash equality binds content, not authenticity, current permission, ownership, revocation or asset rights. CON-02 and EVAL-04 require downstream evidence beyond these pure tests.
