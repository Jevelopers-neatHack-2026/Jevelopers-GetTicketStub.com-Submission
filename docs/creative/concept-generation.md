# Parentless concept creation

The local Creative API implements `concepts.create` as a distinct `CreativeApiRequest` 1.1 operation. Existing operations and stored result shapes remain on the exact 1.0 request contract. The public declaration uses a separate 1.1 union arm and `CreativeConceptBatchResult` response; the runtime rejects concepts on 1.0 and rejects legacy operations on 1.1. This local extension has not been ratified as the canonical C01 catalog or accepted by external owners.

The request carries a brief ID, a plan ID, the requested count, and an ordered list of `{ asset_id, role_ref }` references. It does not carry permission proof, trusted policy, settlement evidence, provider claims, or arbitrary image bytes. Runtime ports supply the current brief, research package, plan, policy, configuration, prompt template, package reference bytes, and asset-permission evidence. The API binds each reference to that current package and checks its tenant/project scope, source, content hash, native-decoded media type and dimensions, byte limits, permission action, and expiry before dispatch. Count, time, reference, and budget limits come from the trusted policy port.

Each requested concept is an ordered independent slot with its own logical operation, C03 reservation, billable attempt, transport attempt, provider request identity, usage observation, response bytes, and lineage. Initial candidates retain `parent_version_id: null`; authorized source images are not converted into a fictitious artwork parent. The native image adapter uses `POST https://api.openai.com/v1/images/edits` with one repeated multipart `image[]` part for each authorized reference, one prompt, and no synthetic mask. The official Images reference describes this edit operation as accepting one or more images and its HTTP example sends repeated `image[]` parts; this was checked on 2026-10-11 in the [Create image edit reference](https://developers.openai.com/api/reference/resources/images/methods/edit). The intercepted local test also checks the exact ordered byte hashes, endpoint, and absence of a parent or mask. The implementation has no automatic SDK retry.

Candidates and their artifacts are published through the existing `CreativeVersionStore` prepare/commit path and the concepts batch record in one owner-backed SQLite transaction. Generic version lookups, list, compare, inspect, restore, and concept lineage resolve the same immutable sibling IDs. Neither a pre-commit stage nor an uncommitted candidate is visible through the public version API. The selected-version pointer is not advanced by concept creation.

The result reports ordered candidate and progress lists with `completed`, `partial`, `running`, `unknown_hold`, or `cancelled` status. A completed candidate is replayed from its immutable stored result and is not regenerated. Known failed slots may retry only with a new C03 reservation and fresh billable/transport identities. A durable staged response resumes with its exact original bytes and attempt after process restart. Unresolved usage or financial exposure keeps the original attempt held and blocks further dispatch; a trusted matching C03 settlement can resolve the financial hold while preserving an unknown provider outcome. The malformed-raster case therefore returns a partial result with no public version when C03 confirms a complete mapped charge, while an unmatched or incomplete observation remains `unknown_hold`. Caller request fields, native response JSON, and usage-mapper output cannot forge a settlement.

The runtime rechecks current job ownership, lease, brief, permission, budget/deadline, and cancellation at each owner boundary and performs a synchronous owner-backed dispatch fence after the final await immediately before POST. A duplicate action joins or replays its existing batch. Cancellation, lease replacement, a lost response, or a late response cannot publish an artifact without the same current owner and attempt; late evidence stays bound to the exact dispatch and does not authorize a new owner's work. Storage helpers snapshot caller-owned bytes and metadata before awaiting decode and preserve caller-owned SQLite `BEGIN`/`SAVEPOINT` transactions on failure.

## Local verification and external boundary

`make check TARGET=concepts MODE=mock` runs the offline reducer, native adapter, actual API/store integration, process-exit recovery, usage and migration cases, strict public consumer, and installed-package journey. The package gate installs a fresh local tarball offline, runs `concepts.create` through the installed public API with two authorized references, verifies two parentless siblings and no-dispatch duplicate replay, checks the unsupported-version negatives, and compiles the strict TypeScript consumer. `MODE=CI` runs the same fixture-only matrix. Paired local evidence uses pinned Node 22.23.3 and 24.15.0 runners; this does not assert the production host's exact Node patch. `MODE=failclosedlive` writes a machine-readable blocked result and exits 2 without reading credentials, dispatching, reserving, or contacting a provider.

These tests use deterministic authorities and an intercepted `fetch`; they prove the repository's local runtime and SQLite path, not live service acceptance. Node 22.23.3 is the evaluated minimum; the production host's exact Node 22 patch remains unknown. Finance has not accepted the concepts operation-kind/rate mapping, and no canonical C01, live account/capability, production host, CE08 deployment, CE09 owner inspection, or CE11 event-sink agreement is asserted by this change. The local one-image-per-concept dispatch rule is the explicit runtime policy; the provider endpoint's broader image-count limits do not determine tenant policy. Live generation, paid calls, model promotion, and external owner acceptance remain separately gated.
