# Creative inspection and bounded repair policy

The public `creative-engine/inspection` package defines deterministic artwork checks, a versioned structured observation format, narrow DecisionPort questions, a review-only report, held-out fixture metrics, and a durable local repair counter. The public creative API wires those checks to persisted design versions, metered observer and DecisionPort attempts, and immutable repair children. It remains a fixture policy (`fixture-policy/1.0`), not an accepted production threshold or canonical external inspection protocol.

## Evaluation order and evidence

The deterministic gate runs before any visual decision. It snapshots the supplied artifact bytes, verifies the artifact content hash, and currently decodes bounded PNG inputs to check file structure, checksum, dimensions, scanlines, indexed palette size, and every packed or unpacked indexed-pixel sample against the palette. A supplied trusted design or artifact identity constrains the candidate rather than being replaced by the candidate’s own ID. It validates the trusted brief and design version, immutable parent identity, declared source references, unresolved facts, and the explicitly supplied asset-use set against the brief’s permission records. A failed check is a failure; missing or uncertain evidence requires human review. A favorable visual answer cannot change these checks.

The public inspection handle preserves a design version’s exact media type only when it has a safe MIME-type shape and passes the public-reference privacy check. Safe but unsupported media types remain unchanged and produce a review-only decode result; private or malformed values fail closed without entering the handle or diagnostic.

The API calls the same pinned bounded decoder used by the image adapter. It decodes PNG, JPEG, and WebP pixels before the observer receives the copied artifact bytes; unsupported formats and malformed or corrupt payloads stop at the deterministic gate. The API-level fixture checks exercise each supported format through durable storage and inspection.

Visual observations are separately sourced records bound to tenant, project, brief, brief hash, design version, parent hash, artifact, and artifact hash. They retain observer/model/configuration identity, source reference, uncertainty, structured findings, and usage completeness. The question builder exposes only allowlisted observation codes, source hashes, and validated prior answers. It never sends raster bytes or raw image content to JEV. A report is limited to `acceptable_for_review`, a bounded repair recommendation, human review, refusal, or failure. It cannot approve artwork, establish legal rights, or certify print readiness.

The host supplies the trusted scope and the pre-eligible repair-action intersection. Inspection does not grant asset rights, unlock controls, authorize spending, or dispatch an operation. The API rechecks current design and brief authority at each asynchronous boundary and in the final publication compare-and-set. It carries the exact checked asset proofs, including their expiry, through observer and both DecisionPort dispatch fences; the final synchronous send check runs after the last awaited job authorization. The report publication transaction checks proof expiry and same-database invalidation fences after the final stage, so a stale proof cannot complete the report.

A repair request must match a completed inspection action and report hash, complete trusted owner usage evidence, eligible `image.edit`, current selection, and the original immutable root lineage. The exact root claim and original start/deadline remain bound to the repair job through pre-reservation, post-await dispatch checks, cancellation/recovery, and same-connection publication. An expired or cancelled claim cannot reserve, send, or publish; claims stay counted if a response is held or publication rolls back. Only a current claim allows the ordinary edit/C03 path to create an immutable child; it cannot overwrite the inspected version. The SQLite repair controller carries the root lineage’s fixture attempt, elapsed-time, and simulated-unit limits across restarts and competing workers. It is not a Finance ledger, budget authority, provider executor, or permission to perform an edit. Unknown repair cost or usage remains unknown and prevents a new bounded claim. Finance quotes, acknowledgements, grants, and actual provider attempts remain separate injected authorities.

## Decision questions

The inspection questions use the existing C02 DecisionPort request/result contract. The host supplies the first trusted operation context and its authorized C03 reservation/attempt data; the first builder returns the frozen C02 request for two independent questions: a Noul probability of a supported defect and a Score over the versioned visual-quality legend. A dependent Choice request is prepared only after schema-valid first-stage answers. It requires a second trusted operation context, a distinct request and billable-attempt identity, and explicit links to the first request, plan, and inspected subject. It receives only normalized first-stage answers plus those content references. Reusing one reservation is neither assumed nor required. Noul has one probability and does not contain a separate confidence field. Invalid answer keys, unsupported model or schema versions, mismatched Score legends, fabricated confidence, timeout, cancellation, abstention, refusal, or injected instructions cannot add an action or expand scope; they produce an unavailable or review-required result.

The evaluator accepts only requests created from the same in-process plan and validates each result against its exact request and trusted scope. Both C02 requests carry the exact design/artifact IDs and the first request includes subject and plan hashes; the dependent request adds the first result hash. The plan binds the hash of the full validated observation, including observer/configuration and usage metadata, while only its structured, allowlisted projection crosses into the DecisionPort. The evaluator carries subject, plan, stage-request, policy, model, and decision-context hashes into the decision. The report checks those references against the exact deterministic inspection and full validated observation; an unbound or unsupported favorable decision becomes human review. This process-local provenance check is not a signature or a durable external acceptance proof. Public observer, DecisionPort context, and repair references are bounded and reject credential-shaped identifiers; sensitive values are never echoed as IDs.

The model identifier is pinned to `jev-1.13.0` in the fixture request context. Moving aliases are intentionally not selected by this module. This is a compatibility proposal for an injected DecisionPort consumer, not a statement that TypeSafe or another owner has accepted this question set, model policy, or transport. The provider documentation describes available model identifiers and Noul’s output shape, but does not establish account access or live acceptance: [TypeSafe model catalog](https://docs.typesafe.ai/models) and [Noul primitive](https://docs.typesafe.ai/primitives/noul) (checked 2026-10-10).

## Durable local repair limits

The SQLite controller binds each inspection to its trusted tenant/project/brief/design scope and exact brief/design hashes. Its fixed fixture limits are two repair claims, 60 seconds, and three simulated units across reopen/restart, duplicate calls, cancellation, and concurrent workers. Claims and completion records are idempotent by action identity. New claims and first completions read the authoritative clock after acquiring SQLite write ownership, so waiting on another writer cannot extend the limit; duplicate historical outcomes remain idempotent replays. A result recorded after cancellation or expiry remains non-publishable. The controller’s status only records local limits; a consuming API must independently revalidate its current context and obtain C03 authorization before dispatch or publication.

## Fixture policy and evaluation

The fixture manifest names seven buckets: corrupt integrity, revoked or unknown permission, valid unchanged output, wrong subject, mask drift, poor result, and adversarial observation. The tests also exercise parent/source bindings, malformed answer shapes, trusted DecisionPort context, bounded repair restart and concurrency, report limitations, and held-out metrics. Owner usage completeness is aggregated over every executed observer and decision stage; a completed report never promotes partial or unknown owner evidence to complete, and either state blocks repair. An acknowledged incomplete stage remains held for reconciliation rather than triggering dependent work. Completed API replay reconstructs deterministic failures, observer refusal/unavailability/timeout, observer-only review, first-stage abstention/timeout, dependent-route timeout, and complete decisions from their stored graph without redispatch. Metrics include expected-defect, valid-output, and unknown-label denominators; false-negative and false-repair rates; and human-review/failure counts and rates. A rate with no cases in its denominator is `null`, not zero. If any case cost is unknown, total downstream cost remains explicitly unknown; known subtotals are not represented as full cost.

`promotion_status` remains `not_promoted`. The frozen fixture policy does not establish classifier calibration, Q01 thresholds, a selected vision provider, live JEV execution, owner acceptance, account access, or production quality. Production promotion requires separately reviewed held-out evidence and accepted owner policy.

## Current integration boundary

The local integration is exercised through the public API and the shared durable SQLite store. Inspection stage intents are persisted before transport; an interrupted stage stays `dispatching` and fails closed after restart without redispatch. The offline mock gate includes all six CE-09 acceptance cases, all seven manifest buckets, public declarations, the populated V6 additive migration, codec paths, privacy checks, metering fixtures, repair bounds, and restart behavior:

```sh
make check TARGET=inspection MODE=mock
```

The repository CI matrix runs the offline check and strict package consumer under Node 22.23.3 and 24.15.0. A local passing mock check does not establish live provider access, accepted owner usage mapping, Finance authority, Neatlogs ingestion/readback, an adjudicated Q01 corpus or production promotion, or Node 22 CloudLinux/CageFS/LVE qualification. `make check TARGET=inspection MODE=live` and `make acceptance TARGET=inspection` remain fail-closed until those separate owner and host evidence gates are accepted.
