# Operations contracts: candidate package 0.2.0

Issues #9-14 provide 20 versioned wire exports and a contract-only injected DecisionPort. Every schema is JSON Schema 2020-12, closed to unknown execution fields/enums, with explicit optional/null rules and field classifications. Types and standalone ESM validators are generated; no engine or harness runtime is imported. These are locally implemented candidates. Producer/consumer agreement, authenticated domain integration and release acceptance remain pending.

Use the [maintained catalog](contract-catalog.md) for each schema/type/fixture path. A contract's schema_version is exactly 1.0.0. Foundation definitions and their exact bytes remain unchanged. Package 0.2.0 adds operations exports, dynamic-map declarations and a structural scoped constraint for checkTrustedContext; the foundation ValidationCode union stays closed, while OperationCode adds domain errors. Operation helpers return OperationResult with typed codes and paths. No helper authenticates a caller, posts money, releases a hold, executes a job, grants an approval or performs provider I/O.

## Wire and semantic boundaries

`validateContract` and `parseContract` check wire shape. `checkOperation` or a narrow helper checks invariants using a separately supplied trusted context. Obtain tenant/project expectations, previous state, allowed actions, policy thresholds, current finance records and reference expectations from your authenticated server adapters. Never construct them from the incoming payload. See the [installed consumer driver](../examples/operations-consumer.mjs) and [typed boundary example](../tests/operations-types.ts).

Every reference has contract, exact schema_version, opaque immutable id/revision and content_hash. Its id carries the referenced domain object's existing identity; it does not mint a distinct reference identity. The generic reference ID is a UUID string, while tenant/project/operation/reservation identities retain their distinct branded types. The helper checks reference fields against the independently supplied `context.references` map using paths such as `policy_ref`, `prior_answers/previous` and `reservation/authority_ref`. Missing expected references fail. The map contains authoritative lookup results, not arbitrary caller assertions. References and hashes describe binding; they do not establish access, authenticity, current revocation or current budget authority. Policy/model/checkpoint/finance-resolution records are owned downstream; this package does not invent their implementations.

Contexts use an explicit UTC now, avoiding wall-clock tests or implicit expiry extension. Original strings/decimal scales/hashes are preserved. New money values are exact decimal strings bounded to 128 characters with a declared scale 0-18 and three-letter currency code. Reservations and usage use nonnegative Money; financial projection metrics also permit signed exact decimal values for losses/adjustments. Comparisons use decimal digits and BigInt, never float coercion, currency conversion or ledger aggregation. Currency applicability and real currency policy remain finance-owned.

## Errors and partial failures: SC-08.ERROR

ErrorEnvelope uses a generated stable code/category registry. Messages are fixed safe literals; module/operation, retry hint, blocking condition, side-effect/usage state, validation paths and opaque diagnostic reference remain separate. Diagnostic paths/references are restricted fields and never enter EvidenceProjection. Codes distinguish malformed input, unsupported version/enum/case, forged scope, stale approval, cancellation, timeout, rate limit, partial failure, budget unavailability, unknown side effects and unknown usage. New codes require version/impact review; they cannot silently expand a closed consumer enum.

A timeout is not proof that nothing happened or nothing was billed. Complete provider-reported accounting can accompany timeout, cancellation, partial failure or unusable output. UNKNOWN_USAGE itself cannot claim complete reporting. Retryability is only a hint; it grants no new attempt, spending, approval or capability.

PartialFailure preserves successful item IDs, explicit per-item failures and unprocessed IDs. The trusted batch item set must match exactly without foreign, missing or duplicate entries. Partial acceptance preserves usable successes; all-or-nothing semantic acceptance rejects a batch containing both usable successes and failures. Shapes may be stored as private evidence, but a failed semantic result cannot authorize publication or retry.

## Jobs: SC-08.JOB

JobStatus and JobProgress use queued, running, waiting-for-review, blocked, cancel-requested, cancelled, succeeded and failed. Outcome (unknown/partial/succeeded/failed/cancelled), progress (nullable completed/total), execution state and accounting completeness are independent. Succeeded requires an immutable result reference; failed requires its typed error. Progress cannot exceed total or move backward. A new revision is exactly prior+1 with a new event ID; exact same-revision payloads are duplicate redeliveries, while altered duplicates and stale/out-of-order revisions fail. Terminal jobs cannot resume or advance. A lease change requires a separately supplied trusted lease ID. Harness implements CAS, leases, recovery and durable delivery.

Cancellation is a request with an expected revision and idempotency identity; it is not terminal cancellation or evidence of absent side effects. JobCommandAcknowledgement covers create/status/cancel/correct/resume with accepted/rejected/duplicate/unknown dispositions. Duplicate commands must match recorded identity. Resume after a terminal job is rejected; uncertain execution cannot be reset to not_dispatched by an acknowledgement. Complete usage reports do not clear execution uncertainty. Checkpoints, partial artifacts, lease correlation and error/result references are data; this package performs no workflow transitions.

## Usage and reservations: SC-06.USAGE / SC-06.RESERVATION

UsageEvent distinguishes event/redelivery, usage event, source observation, logical operation, provider execution, billable attempt, transport attempt and nullable provider request identity. Missing provider IDs remain explicitly unavailable. Unit relations distinguish standalone, included subset and unknown relation; duplicate names, missing parents and subset cycles fail. A complete report contains explicit measured units, including measured zero; unknown units are null and never converted to zero. Reporting completeness, valuation basis, money and operation outcome are independent. Known complete accounting can be retained for timeout/cancelled/unknown outcomes with explicit valuation and rate-card references.

`compareUsageIdentity` classifies duplicate observation, superseding observation, same execution or distinct billable attempt. Changed economics under the same immutable observation is a conflict. Corrections use new observation identity and point to the superseded observation under the same execution/billable attempt. Transport retries need not create another billed attempt; separately billed executions remain distinct. The retry-mapping reference is explicit and finance/provider-owned. No deduplication, allocation, posting or reconciliation service is implemented here.

BudgetReservation separates granted/denied/unknown/unavailable decisions from held/consumed/released/expired/uncertain-in-flight lifecycle, execution state and reporting completeness. It binds finance authority, scope, operation/billable attempt, exact held/consumed money, expiry, idempotency, revision and settlement evidence. A complete usage report alone never clears an uncertain hold. Release/expiry/final settlement is refused while trusted execution may still occur. After uncertainty, a separately obtained FinanceResolution context must bind the same tenant/project/reservation/billable attempt, resolved execution state and exact resolution reference. A caller boolean or unbound reference cannot replace that context; finance still authenticates and performs the transition.

ReserveRequest/Result, SettleRequest/Result, ReleaseRequest/Result and QueryRequest/Result are separately exported and fixture-indexed. Requests enforce currency, policy, exact amounts, expected revisions and idempotency. Results bind the exact request ID/key, finance producer and matching reservation identities and lifecycle. Declined/unavailable/unknown results remain distinguishable; no caller-supplied status mints capacity. Competition for capacity, atomic holds, replay storage and real accounting remain cost-intelligence work.

## Financial projections: SC-06.SUMMARY

FinancialSummary declares its period, currency/scale/rounding boundary, metric definitions, original amounts, rate cards, source/event references, included environments/billing modes and coverage. Valuation, settlement, reconciliation, reservation state and reporting completeness are independent. Unknown metric totals are null with unknown status; sub-cent digits and signed values remain exact. Incomplete/unknown source coverage cannot masquerade as complete. Environments and billing modes must match the trusted projection scope. Foreign original currencies require an explicit bound conversion reference; this package neither combines currencies nor calculates any total. Refund, credit, reversal and payment references preserve lineage without defining a competing ledger.

## DecisionPort: SC-05

DecisionPort is an injected interface below engines and harness; bindDecisionPort wraps a supplied implementation with request/result checks and immutable request/context snapshots. The wrapper makes no provider call itself, performs no retry and cannot create authority. The server must independently authenticate scope and supply a current finance budget record, allowed question IDs/candidates, policy thresholds, attempt limit, permitted score profiles, reference expectations and deadline context before invocation. The handler owns transport and all live authorization gates.

Requests carry bounded questions, stable request/batch IDs, policy/model/state/budget/cancel references, attempts/deadline and prior-answer references. Questions in one batch are independent. Cycles and sibling-answer dependencies are rejected; a dependent stage instead references an immutable prior answer bound in trusted context. Results cannot add questions/candidates or lower confidence policies. Partial/all-or-nothing handling is explicit.

Choice validates an allowed selected candidate, full normalized probability map, maximal selected probability and confidence. Score validates an ordered level distribution, corresponding legend, bounded probability-weighted index and confidence. Noul carries only its probability, with no invented confidence. Its trusted uncertainty band determines review. Distribution and weighted-score tolerance are 0.000001 for this candidate. This differs from the harness wire tolerances and requires a reviewed adapter; no normalization or renormalization occurs. These structural semantics follow the [provider Choice](https://docs.typesafe.ai/primitives/choice), [Score](https://docs.typesafe.ai/primitives/score) and [Noul](https://docs.typesafe.ai/primitives/noul) references, without claiming consumer acceptance.

Score profiles are mandatory. structured-index-v1 retains arrays/structured inert descriptions and an index legend. ei-string-v1 preserves opaque criteria/legend strings and separately declared ordered index labels. The original EI string-only rule remains untouched. adaptScoreProfile returns both the complete source and explicit target with accepted_migration=false. Structured descriptions can be canonically encoded into the string profile and reversed; opaque legacy text is rejected as unrepresentable rather than silently parsed or rewritten. Official provider documentation does not resolve the EI/creative owner disagreement. Exact owner decision, lossless migration fixtures and consumer pins remain release blockers under SC-05.3.

Results distinguish complete, review, partial, unknown, abstain, unavailable, timeout, cancelled and malformed. Low confidence and Noul uncertainty produce explicit review reasons. An unusable or uncertain decision can still carry complete usage accounting and a bound usage reference. Accounting never implies usability, successful side effects, release eligibility or an automatic paid retry.

DecisionReceipt binds request/result/question/answer canonical hashes, immutable state, policy/model, scope, request/batch and operation/billable attempt IDs, decision time, normalized result, usage and review reason. Changed answers, legends, hashes or modes fail. The receipt is private decision evidence, never artwork approval or purchase authority.
