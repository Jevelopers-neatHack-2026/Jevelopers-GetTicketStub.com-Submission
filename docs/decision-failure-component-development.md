# Creative → Harness → Creative decision failure DEVELOPMENT

This standalone component contributes narrow IE-05B decision-failure evidence. It
runs a request created by Creative inspection through the actual Harness public
DecisionPort, then feeds that exact result to the same installed Creative route
consumer. Existing scenarios, acceptance criteria, components and producer pins
remain unchanged. No OwnerResponse, Assembly or full issue acceptance is emitted.

```sh
node decision_failure_component_tests/run.mjs /exact-harness-ee86ce2 /exact-creative-46766 /new-output
```

Exact sources are Harness `ee86ce2f5917a961a0903591eb13523cf899e54f` and Creative
`46766f97172af679f533d75106d7665a873e8b96`. Harness's unchanged lock installs Creative
archive `e4fa66488f31577f516b27238e945a1fb3c2143f`, whose source tree is identical.
All tracked input bytes are checked. The installed Creative files are independently
byte-joined to the exact source. npm's three `.gitignore` → `.npmignore` packaging
renames are recorded; file contents must still match. Node is 22.23.3, TypeScript
5.9.3 and Neatlogs 1.1.28. Harness declares no exact npm pin; its actual version
and installed npm bytes are recorded rather than inventing a producer requirement.

Bootstrap creates a private Harness clone and runs the locked command
`npm ci --ignore-scripts --no-audit --no-fund`. HOME, cache, TMPDIR and PATH are
explicit and credentials are not inherited. Install networking ends before the
component executes. Source and all installed dependency bytes are rechecked after
execution. Source directories and previous component lanes are not modified.

Creative imports resolve through the installed package's declared ESM public
entry points. Inspection handles, plans, first requests and route consumption
remain in one ESM graph; no WeakMap brands are reconstructed. Separate Creative
source imports provide only owner fixture helpers for synthetic briefs, versions
and PNG bytes. The observed asset permission is synthetic fixture data, not rights
evidence. No generated image, renderer, C03 admission, Apply or repair is executed.

The first scenario is a mandatory benign first-stage complete control. Actual
Creative emits
`defect_present` Noul and `visual_quality` Score questions, Harness sends exactly
one intercepted request and returns complete, and Creative creates a dependent
`next_step` request. That control does not dispatch its follow-on request; the
separate Choice controls below do. If this control
fails, the matrix stops rather than qualifying unrelated fixture/configuration
errors as successful denials.

The original fourteen independent faults cover timeout/cancellation before and
after send,
429 and 503, malformed and truncated JSON, wrong question keys, invalid Score and
probability distribution, missing usage, uncertain Noul and low Score confidence.
The recorded expected states follow the actual owners: malformed responses return
`unavailable`, while uncertainty returns `review`. Creative must return exactly
`review_required` with that status, without constructing a dependent request.
Before-send cases require zero DNS/request/write counters; every other case must
reach exactly one intercepted send and the three fixture dispatch callbacks, with
no retry. Known token counts are retained where the owner validates them even when
answers are invalid. Otherwise usage remains explicitly unknown, with no zero-token
or zero-cost substitution. Monetary cost remains unknown in every receipt.

Harness's exported test transport and its native HTTP/DNS/TLS/fetch guard are loaded
before owner execution. A blocked guard self-test and per-case metric deltas prove
the guard remains active outside the targeted interceptions. This is fixture-level
network interception, not a claim of the formal runner's OS egress containment.
The synthetic key, eligibility, reservation and callbacks grant no actual provider
or Finance authority. Owner `billing_mode: live` fields are retained unchanged,
inside enclosing `intercepted_mock_only`, synthetic-authority receipts with paid
execution disabled and acceptance false. No actual provider call is required.

Nine additive executions cover the remaining supported boundaries:

- A mandatory valid Choice control runs the real generated `next_step` request
  through Harness and passes both actual stage results to Creative's
  `evaluateInspectionDecision`. It produces `acceptable_for_review` /
  `not_an_approval`. Unknown-option and invalid-answer-enum cases use candidates
  from that actual request and produce the final `needs_human_review` fallback.
  These are two declared batches with distinct request, billable, reservation and
  transport identities and linked logical/correlation identities. Each batch sends
  once. They are not retries; no Apply or action execution follows. The second
  stage's explicitly synthetic record-permit callback checks its distinct ID.
- Raw Score `NaN` text and the distinct valid-JSON overflow token `1e309` are
  retained exactly, with hashes. The evaluator never substitutes JSON `null` for
  a non-finite test. Actual Harness rejects both with unavailable/unknown usage.
- Removing the optional provider-request header from both intercepted header
  representations leaves a complete result and valid 10/4 token usage, with
  `provider_request_ref` genuinely absent. No mandatory receipt is invented.
- Valid responses delivered after timeout or cancellation cannot change the
  settled result, its hash, Creative's review fallback or wire counters. The
  wrapper captures and later releases only the owner's intercepted callback and
  bounded chunks. It never delegates to native networking. A separately deferred
  synthetic permit resolves after cancellation with zero writes. The test runner
  also treats unhandled late exceptions/rejections as failures.

Existing cases now explicitly forbid invented Noul confidence/probabilities and
invented answers or confidence on unavailable answer records. These assertions use
already-executed cases rather than adding duplicate fault executions. Native
provider abstention outside the supported wire schema and cross-invocation
financial replay remain unqualified boundaries.

Each case retains the CE request, actual Harness result, actual CE consumer return,
plan/subject/target and before/after hashes, input fingerprints, bound attempt and
reservation/transport identities, wire body/counters and callback order. Request
and result hashes must remain unchanged during consumption. Transport headers and
key-bearing options are never uploaded. Reports use portable path labels. Outer
processes have bounded output, deadlines and process-group termination; uncertain
termination produces a failed receipt and preserves private files. Only confirmed
owned private directories are removed. Failed cases and command receipts remain.

`scenarios.test.mjs` runs serially with `DF_HARNESS` (installed private source),
`DF_CREATIVE` (exact fixture source), `DF_OUTPUT` (new empty directory), private
HOME/TMPDIR and Node22.23.3. It executes actual APIs, never producer test suites.
`receipt.test.mjs` takes `DF_CASES` and mutates those actual reports to prove wrong
consumer results, excess sends, hidden bootstrap failures, identity drift, invented
free cost/zero usage, missing cases and authority upgrades cannot qualify. It also
runs inert timeout/overflow and quarantine controls. `DF_TEST_EVIDENCE` retains
those explicitly synthetic negative-control receipts.
