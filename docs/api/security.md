# Finance authorization and data handling

## Authority boundary

Every scoped finance operation resolves its exact operation through `authorizeFinanceOperation`. The shared `FINANCE_OPERATION_POLICY` assigns a local permission, data class and allowed principal kinds to implemented operations and reserved future actions. `RuntimePorts.financeAuthority.authorizeCurrent` must resolve the principal from the host's trusted issuer and recheck current tenant membership or service grant, revocation state, requested scope, exact operation and permission on every invocation. The host must not infer finance permission from an application role, `TrustedContextPort`, request fields, approvals or a broad read/write role.

The decision must repeat the requested operation, permission, full tenant/project/environment/billing-mode/actor scope, active principal kind and actor ID, a nonempty current membership or service-grant revision, a unique decision ID, and valid `verifiedAt`/`expiresAt` timestamps. The trusted clock is read after each asynchronous authority response, immediately before time validation. The local boundary allows a decision verified within the last 60 seconds and a decision lifetime of at most five minutes. Expired, stale, mismatched, inactive, or wrong-kind decisions return a generic `FORBIDDEN_SCOPE`. Malformed decision and request values return bounded generic errors without copying authority data. Missing, throwing, null, or unusable authority returns `SOURCE_UNAVAILABLE`; an unavailable result never counts as a positive authorization.

The existing v2 `PricingActionAuthorityPort` remains as a compatibility bridge for already published pricing callers. Its action-specific scoped result goes through the same central gate and is queried again before estimate replay, catalog access, each contract-time/dimension/bound-evidence resolution, and snapshot persistence. Every compatibility decision must carry a fresh issue time (within 60 seconds) and remain unexpired; the existing port's longer expiry shape is preserved for wire/runtime compatibility. New host integrations should provide `FinanceAuthorizationPort`, which also bounds decision lifetime to five minutes and carries current membership/service-grant revisions. Neither interface in this package contains the upstream GT issuer adapter, accepted GT grant spellings, or the issuer-to-billing-mode mapping: those remain unresolved, so this package does not claim a live GT integration. The finance permission names below are package-local policy IDs and must be mapped only by a separately reviewed host adapter.

`TrustedContextPort` remains in legacy runtime shapes for source compatibility, but it grants no permission. A request's explicit `scope` is an authorization request, not proof of identity. Ledger SQL independently binds tenant, project, environment, and billing mode. Foreign scopes are denied before ledger connection or row lookup when the current authority does not grant that exact scope.

The policy also reserves permissions for unreleased actions; a declaration does not make an operation available.

## Source facts, response fields, and retention

| Field group | Access rule | Current exposure |
| --- | --- | --- |
| Tenant, project, environment, billing mode, actor | Required to authorize every operation; host resolves the actor and exact scope | Included in the ledger projection's requested scope; never copied into the safe export projection |
| Exact money, usage quantities, completeness and lifecycle status | Available only after permission for the corresponding estimate, ledger, summary, or budget operation | Implemented estimate, ledger, budget and reporting paths return scope-bound results; typed unavailable operations return no financial rows |
| Request/event/correlation/attempt IDs, customer/order/provider/workflow identifiers | Restricted operational facts; not broad read permissions | Not included in the safe export projection; do not include in authority errors or logs |
| Source URLs, evidence references, payloads, prompts, addresses, source blobs | Restricted evidence; resolve only through an authorized evidence port and retain only what the leaf needs | Pricing rejects credential-bearing URLs; ledger quarantine stores a payload hash rather than raw unsupported payload; safe exports omit evidence and source refs |
| Catalog versions, rate-card/rule/FX references | Protected immutable pricing data | Returned only through pricing estimate/catalog operations; not copied into the export allowlist |
| Budget limits, holds, settlement and dispatch proofs | Restricted budget state/action evidence | Reservation, revalidation, dispatch and policy paths are locally implemented; public settle/release and expense-adjustment posting remain unavailable |

Public request schemas accept only documented fields. Before hashing or persistence, supported ledger events reject evidence URLs with credentials, query strings, fragments, or sensitive free text and require reviewed quantity names. Quantity values and completeness remain unchanged; an unknown measure label fails validation instead of being returned or persisted as source prose. The reviewed finance vocabulary includes `input`, `input_tokens`, `output_tokens`, `reasoning_tokens`, and `cache_write_tokens`; incomplete and unknown observations retain the documented missing-field descriptors `all`, `usage`, `providerAttemptId`, and `billableAttemptId`. These identifiers do not make arbitrary metadata trusted. Reviewed dimensions may contain ordinary spaces; credentials, addresses, prompt text, and links are rejected. The ledger persists normalized financial events and source identity/content hashes needed to enforce idempotency, lineage, and immutable projection behavior. Unsupported ledger payloads are not stored: quarantine records retain the scoped identifiers, a safe reason/version, payload hash, and opaque diagnostic reference, never the raw payload. Ledger projection queries constrain all four financial scope dimensions and return amounts, quantities, completeness counts, and the requested scope. Ledger snapshots remain append-only.

Pricing catalogs are immutable and scope-bound. Catalog source URLs must use HTTPS and must not contain user information, query strings, or fragments, which prevents signed URL credentials from entering catalog rows. Estimate evidence ports receive the exact scope, actor, event/reference identifiers, effective instant, currency, and selected catalog references required for their decision. A reference hash alone is not evidence. The caller rechecks authorization before each evidence lookup and before persisting an estimate.

The legacy safe summary serializer uses a narrow allowlist and exposes only the fixture-backed `expense` metric from the pinned proposal. It excludes tenant/project, event, customer, order, correlation, evidence and source-reference fields. The configured snapshot-backed v2 exporter is a separate path: it reads a verified stored query snapshot and applies a finite Finance-owned proposal dictionary before preparing JSON/CSV artifacts. Both paths use the hardened CSV encoder. The [exact tested registry mapping and original synthetic consumer ACKs](cfo-ai-handoff.md#accepted-synthetic-handoffs) are recorded. Broader policy/canonical adoption, later producer additions and actual host/current-grant/fence adoption remain subject to their owners; neither path delivers data to CFO.ai. Never serialize a raw `FinancialSummary` or wrapper.

Errors use the published bounded safe envelope and do not copy raw authority failures or request fields. Tests use private canary markers to check safe errors and exports. There is no application logging adapter in these leaves; a host adapter must log opaque decision/request references and safe status only, never the raw request, source evidence, credentials, or provider payload.

## Database roles and legacy-row handling

Additive migration `0006_finance_security_roles.sql` creates the non-login `ci_finance_owner`, `ci_finance_migrator` and `ci_finance_runtime` groups and audits privileged host paths. Later migrations grant scoped runtime operations on accounting snapshots, budget reservations/authority bindings, usage-intake tables and reporting snapshots in addition to ledger and pricing. The migrator has owner membership and RLS bypass for controlled migration/audit work; runtime grants are constrained by each migration's operation needs. Before changing ownership or granting runtime access, the migration audits role membership paths, ADMIN OPTION memberships, owners, database/schema CREATE and finance schema table/column/sequence/function ACLs, explicit parameter ACLs, and executable privileged routines across catalog, user, and extension schemas. Parameter review checks effective `SET` and `ALTER SYSTEM` grants through PUBLIC, direct, inherited, and SET-reachable roles. In particular, no runtime principal may change `session_replication_role`, which could disable the identity-binding triggers. It fails closed when it finds an unreviewed privilege path; it does not remove unrelated host memberships, parameter grants, or direct object grants. A database administrator must review and remediate the reported host configuration, then rerun the migration. Run the same role, parameter, and routine audit after provisioning any new runtime login or changing host grants, since a later host-side change cannot be checked by an already applied migration.

The effective-role audit also rejects inherited or SET ROLE paths into PostgreSQL's reserved `pg_*` predefined roles. Those roles include capabilities that their `rol*` attributes do not describe, such as server-file access, server-program execution, broad data access, and monitoring. Routine review checks callable `SECURITY DEFINER` routines in user and extension schemas, PostgreSQL's server-file and large-object file routines, and protected members of `adminpack`, `dblink`, `file_fdw`, and `postgres_fdw`. SQL-standard invoker routines are checked through a transitive dependency walk that combines `pg_depend` edges with parsed `prosqlbody` function calls, including chains that cross between those edge types. Function checks include default ACLs, `PUBLIC`, direct grants, inherited grants, and SET-only grants, with schema `USAGE` included in the effective path. This is a capability-specific policy: ordinary built-ins such as `version()` and `current_setting()` remain available, and the application-required `finance_scope_matches` function is retained. No privileged routine exception is currently reviewed. Regression probes read only the harmless in-cluster `PG_VERSION` file; they make no claim about arbitrary-file or absolute-path access. A future privileged exception requires an exact, narrow reviewed signature before the routine is retained as runtime-callable.

When the preflight rejects an unsafe configuration, PostgreSQL rolls back the migration transaction and `0006` is not recorded as successful. Existing host memberships, parameter ACLs, and routine grants remain active until a database administrator repairs them explicitly. A login rejected during provisioning can still exercise its pre-existing privilege before that repair. After removing or narrowing the identified grant, rerun the migration and verify denials through the actual runtime login; the rejected migration itself does not revoke host privileges.

The runtime role has no DDL, owner, superuser, create-role, create-database, or RLS-bypass privileges. A host provisions separate runtime and migration logins, keeps both credentials private to their services, and uses `SET ROLE ci_finance_migrator` for migration administration. A one-time privileged bootstrap is still required to create the non-login groups and establish ownership; the migration login itself has no superuser, create-role, or create-database privilege. The offline PostgreSQL harness creates random runtime and migration logins for the database-backed suites, exercises scoped APIs through the runtime login, schema DDL and privacy audits through the migration login, and uses the bootstrap connection only for setup and test-only raw assertions. No credential is stored in the repository.

The implemented database transactions bind scope only after the host authority accepts the exact tenant, project, environment, billing mode and actor. RLS policies require transaction-local scope on ledger, pricing, accounting-snapshot, budget, usage-intake and reporting-snapshot rows; unbound runtime queries return no rows. A request cannot set those values through an API field or broaden authorized scope. The application must not expose its database login to an end user or use it outside the trusted service boundary. PostgreSQL custom settings can be changed by a holder of the runtime login, so that credential is part of the trusted backend boundary; direct SQL access with it is outside the host identity protocol.

The additive migration scans string values in supported historical event payloads and evidence references, plus projection quantity labels. It does not mistake JSON property names or reviewed measure names such as `token` for private content. It records only the content hash, scope, and a bounded reason in `financial_privacy_quarantine`; it never rewrites immutable history or copies the unsafe value. RLS hides ledger events and projection snapshots for an affected scope from the runtime role while preserving the original rows for restricted audit. The audit function can be rerun by a migration administrator after a controlled legacy import.

Filtering a sensitive predecessor, correction, reversal, or snapshot out of ordinary rows can change money, completeness, or lineage. Therefore every implemented ledger append/retry, unsupported-payload quarantine, and projection/replay checks the authorized scope's privacy audit metadata before looking up source heads, idempotency bindings, event ancestry, or snapshots. Those paths and the migration audit take the same transaction-scoped lock for an affected scope, so a replay cannot race the audit and persist a misleading replacement snapshot. If any event or snapshot in that scope is quarantined, the operation returns the existing typed `SOURCE_UNAVAILABLE` envelope with an opaque diagnostic and creates no replacement snapshot, ledger row, or unsupported-payload quarantine entry. This deliberately makes the affected financial scope unavailable until restricted review; it never reports a successful zero, omits a hidden economic fact, resurrects a superseded predecessor, or changes an immutable hash. Clean scopes retain deterministic as-of snapshots and exact replay.

## Downstream handler obligations

Before adding or completing any current unavailable handler, call `authorizeFinanceOperation` before row lookup, retry/replay lookup, source/evidence resolution, export generation, or mutation. Recheck current membership/revocation for each separate read, retry, evidence lookup, and export delivery attempt. Bind every row predicate and mutation to tenant, project, environment, and billing mode. Use the least-privilege permission from the matrix, preserve opaque safe errors, and project only fields allowed for that handler's data class. Any new ledger quarantine or snapshot reader must use `ledger.resolveQuarantine` or `ledger.readSnapshot`; it must not reuse append/project service grants. Extend the restricted runtime grants and RLS tests only for the data operations a reviewed handler requires.

The local synthetic fixtures and tests exercise this policy only. They are not production identity, issuer, host authorization, or live provider evidence.
