# Creative API v1

`creative-engine/api/v1` exports a typed, non-UI API and handler factory for the local creative workflow. Existing operations use `CreativeApiRequest` schema `1.0`; parentless concept creation is the separate `concepts.create` arm in schema `1.1`. A 1.1 request is valid only for `concepts.create`; other version/operation pairs fail with a typed `unsupported_version` error. Public declarations are ESM `.d.mts` files and are checked under strict TypeScript NodeNext resolution. The deterministic planner is also exposed at `creative-engine/planning`.

This package supplies orchestration and validation around injected ports. It does not create an application identity, provider transport, finance authority, approval issuer, storage service, or renderer. With no required port injected, the operation returns a bounded `unavailable` response and cannot report a successful result. `MODE=live` is not implemented. A passing mock check is local conformance evidence only.

## Version and field compatibility

| Contract used by this API | Accepted version | Compatibility behavior |
| --- | --- | --- |
| `CreativeApiRequest` | `1.0` for existing operations; `1.1` for `concepts.create` only | Exact operation/version pairing. The 1.1 addition leaves all 1.0 operations and payloads unchanged. Other versions and cross-version operation pairs return `unsupported_version`. |
| `CreativeBrief`, `EditPlan`, `DesignVersion` | `1.0` | Each is validated by its pinned local contract before use. The API does not infer a newer version or downgrade a newer object. |
| `DecisionPortRequest`, `DecisionPortResult` | `1.0` | Validated against the pinned DecisionPort contract and request policy. An unsupported schema or policy fails closed. |
| Metering proposal, approval/handoff proposal | Their published local proposal versions | These are injected adapter boundaries. They do not establish external owner acceptance or live-service compatibility. |

The API request envelope requires `contract`, `schema_version`, `event_id`, `request_id`, `tenant_id`, `project_id`, `correlation_id`, `producer`, `occurred_at`, `ingested_at`, `environment`, `billing_mode`, `source_refs`, `operation`, and `payload`. `action_id` is required for `generate`, `edit`, `concepts.create`, `inspect`, `restore`, `cancel`, `handoff`, `brief.create`, and `brief.invalidate`; it is optional for the read operations `list`, `compare`, and `job.status`. The payload requires every operation-specific field shown by the `CreativeApiRequest` TypeScript union. Only `generate` and `edit` may include optional `decision_request`; only `list` may include optional `limit` and `cursor`.

The v1.0 and v1.1 envelopes and their operation payloads reject unrecognized keys. Neither version negotiates additive request fields: clients must send only fields declared by that version and must not depend on unknown fields being preserved. Nested `EditPlan`, DecisionPort, brief, design, metering, and handoff values are checked by their own versioned validators; the API does not reinterpret unknown nested data as facts, permissions, actions, or authority. The local ResearchPackage normalizer separately supports the `ResearchPackage` alias for `EventIntelligencePackage` 1.0 and 1.1. `brief.create` obtains the current package through a trusted port; the caller cannot submit verified facts or owner permissions as request data.

## Parentless concept creation

`concepts.create` uses the exact v1.1 payload `{ brief_id, plan_id, requested_count, references }`, where each ordered reference contains only an `asset_id` and opaque `role_ref`. Trusted ports resolve the current brief, research package, plan, policy, configuration, prompt template, reference bytes, and permission evidence. The request cannot supply permission proof, policy snapshots, settlement results, or caller-owned artwork bytes. Each concept gets a separate attempt and an initial `DesignVersion` whose `parent_version_id` remains `null`.

The native adapter sends only the authorized reference bytes as repeated multipart `image[]` parts to the documented `/v1/images/edits` operation, with no invented parent or mask. The official [Create image edit reference](https://developers.openai.com/api/reference/resources/images/methods/edit) and its multipart example were verified on 2026-10-11. The local intercepted test asserts the exact endpoint, count, order, and reference byte hashes. Each result is committed through the shared version/artifact store, then resolves through public `list`, `compare`, `inspect`, and `restore` operations. Concept creation does not advance the selected-version pointer.

Results include ordered `candidates` and per-slot `progress`. A completed action replays its stored result without another provider dispatch. A staged response resumes using the same attempt and exact bytes after restart. Known failures use a new metered attempt; unresolved or incomplete usage keeps an `unknown_hold` and blocks more work. Only the matching C03 settlement observation and acknowledgment can resolve a financial hold; the API ignores caller, native response, and mapper settlement claims. A confirmed charge with malformed output remains a paid failed/partial operation and publishes no version. See [parentless concept creation](../creative/concept-generation.md) for detailed local behavior and limits.

This v1.1 operation is a local integration extension, not canonical C01 or Finance approval. The type and runtime checks do not authorize live calls or establish external account, storage-host, inspection, or event-sink acceptance.

For `list`, `limit` defaults to 20 and must be an integer from 1 through 100. The opaque cursor is limited to 1,024 characters and is bound to the caller's tenant, project, and brief. Ordering is stable across pages: descending `occurred_at`, then ascending `design_version_id`. A cursor from another brief or scope is rejected.

## Trust and ownership

The application supplies a trusted actor context separately from the request. The runtime checks expiry, required permission, and exact tenant/project agreement before using the request. A request cannot select its own trusted actor, tenant, or project. The storage and job adapters receive the trusted scope on each lookup and write; the runtime also verifies returned records before using them. Storage adapters must implement their own atomic write conditions. `saveDesignVersion` compares the canonical brief hash plus the expected current design ID and hash. `selectDesignVersion` compares the canonical brief hash, target design hash, and selection revision, then changes only the selected pointer.

Mutation requests require an `action_id`. The job adapter's `begin` operation must atomically return the existing job for a matching identity, reject the same identity with a different request hash, or create one job and lease. Results are replayed only after the stored result is revalidated against current scoped records. List cursors are opaque, bounded, and tied to one tenant, project, and brief. Pages use a deterministic ordering by descending `occurred_at`, then ascending `design_version_id`.

`jobs.authorizeDispatch` is a required atomic fence between a running job's lease and each provider, DecisionPort, inspection, or handoff transport attempt. It receives a `context_fence` with the exact canonical brief hash, optional design ID/hash, and, where current selection matters, the expected selected design ID/hash (including explicit `null` for first generation). The adapter must compare this fence against authoritative records in the same transaction that inserts the dispatch intent, alongside cancellation and lease ownership. A mismatch returns `stale_context`; cancellation or lease replacement returns `cancelled` or `lease_lost`. None of those results starts a transport call. If dispatch authorization takes the fence first, a later context change can block publication but cannot erase the transport attempt or its financial exposure; metering and reconciliation remain separate authorities. Every retry needs its own transport identity and authorization. Duplicate intents must match the same job, attempt, transport, lease, and context fence. `completeIfActive` receives a `publication_fence` and must compare it in the same transaction that publishes the result; an operation whose cancellation or context change wins cannot publish.

After the final awaited authorization and any external transport acknowledgment, the runtime calls the required synchronous `jobs.assertDispatchCurrent` owner check immediately before returning a send permit. This check re-reads the current job status, lease token and expiry, exact dispatch intent, and context from the durable owner; it cannot be implemented as an async wrapper around `authorizeDispatch` or trust status supplied by the caller. `cancelled`, `lease_lost`, and `stale_context` results fail closed before the adapter can send. The synchronous check supplements the atomic intent authorization and current rights/deadline checks; it does not replace Finance acknowledgment, reservation, or later reconciliation.

## Operations

`brief.create` requires `creative.brief.create`, loads research through the trusted planning adapter, and accepts only customer preferences, artistic intent, additional required fact keys, fact-correction proposals, locks, and an optional expected brief hash. It deterministically returns a scoped `CreativeBriefPlan` without provider or model dispatch. Immutable brief history and the current brief head are committed with the idempotent action record on the CE08 SQLite connection. Missing or conflicting required facts remain clarification requests; corrections do not overwrite verified research facts. `brief.invalidate` requires `creative.brief.invalidate` and accepts a trusted event identifier only. The adapter authenticates the loaded event, commits monotonic fact/asset fences and approval-staleness requests before external callbacks, and acknowledges the source only after required application acknowledgments. Replayed acknowledgments are idempotent. These operations do not create a rights authority or permit user JSON to assert verified facts or grants. See [creative brief planning and invalidation](../creative-brief.md).

`generate` and `edit` accept a validated `EditPlan`; the latter also supplies the exact base `design_version_id`. Optional DecisionPort work uses the injected `decisionPort` and is validated against the locally pinned request and response contract. Image dispatch is passed to the injected provider port only after reservation, in-flight acknowledgement, and job dispatch authorization. The returned immutable `DesignVersion` is saved through a compare-and-set storage operation. `composition.update` returns typed `unavailable` before routing or reservation until a deterministic composition executor is injected; it never falls through to image editing. `correction.apply` also returns typed `unavailable` before DecisionPort, routing, reservation, or image dispatch until a research-owner correction handoff can update authoritative facts and invalidate dependent creative state.

`inspect` requires an inspection resolver and inspection port. The port receives the initially allocated `transport_attempt_id` and records it before dispatch; usage may report provider and transport identities separately. The runtime reads the stored artifact and decodes its pixels with the same pinned bounded PNG/JPEG/WebP decoder used by the image adapter before calling the observer. The inspection session and each observer/DecisionPort stage intent are persisted in SQLite before transport. A completed stage replays from its hash-checked record; an interrupted `dispatching` or unknown stage fails closed after restart and is never redispatched automatically. Inspection runs through the C03 metering boundary and publishes only a projected result whose tenant, project, brief, design, artifact, and content hashes still match the current scoped records. Nested observer and uncertainty objects use exact allowlists; raw raster data and unknown fields are not returned. Public observation strings are also checked for credential, signed-URL, email, and phone-number patterns on both fresh results and persisted replay; ordinary descriptive prose is preserved, while sensitive content fails closed.

An inspection report can only recommend review or an eligible repair. `edit` may include the exact completed inspection action ID and report hash as `inspection_repair`; the API revalidates the current immutable source and rights context, verifies complete owner usage evidence, and checks the durable root-lineage limits before invoking the ordinary edit route. A permitted repair is an immutable child of its source version and uses its own C03 reservation and dispatch fence. The local root limits persist two claims, 60 seconds, and three simulated units across restarts and competing workers. They do not authorize spending or replace Finance. Unknown usage or cost holds the repair closed; an exhausted limit returns `review_required` before another route, reservation, or transport.

Every public response record is recursively checked for credential-shaped, signed-URL, and personal-data values, including nested optional metadata, design artifacts, approval proofs, and receipts. The check covers fresh responses, stored replay, list, and compare results. Identifier-shaped fields are validated as references, while nullable `parent_version_id` remains null for root versions. The API preserves accepted hash-bound metadata exactly; if any nested field is unsafe, the operation fails closed instead of stripping fields or returning a changed hash payload.

`list` and `compare` are scoped reads. `restore` validates a target immutable version and uses `selectDesignVersion` to update the separate selected pointer by revision compare-and-set; it does not create a new `DesignVersion`. `cancel` first loads and validates the target job in the caller's project before asking the job adapter to cancel it. `job.status` returns a scoped status record without exposing stored result bodies. `handoff` verifies a version-bound approval after dispatch authorization and re-reads the brief, facts, assets, permissions, composition, preview, and design binding around verifier and submission waits before accepting a receipt. A receipt must have a valid UTC timestamp no later than trusted now, at or after handoff creation and approval issuance, and strictly before approval expiry. Completed replay still authenticates the current caller and scope, then validates the stored receipt at its historical consumption time without resubmitting or using expired approval as new authority. The consumer still must atomically consume the approval for that exact binding.

Errors use `CreativeApiResponse` schema `1.0` for v1.0 requests and schema `1.1` for `concepts.create`; success responses follow the same request-version pairing. The envelope contains a stable module (`creative-engine.api`), operation, bounded field path, code, retryable flag, fixed safe message, and diagnostic reference. Adapter exception strings, headers, credentials, and signed URLs are not returned. Trace events use an allowlisted shape, map unknown operations to `unknown`, and omit unsafe identifiers. Public job references accept only bounded opaque identifiers; unsafe stored result references fail closed.

## Injected ports and pending agreements

The public `CreativeRuntimePorts` type describes jobs, scoped storage, provider routing, DecisionPort, inspection, metering, approval verification, handoff, and trace adapters. The repository includes executable fixture adapters for offline checks, not production implementations. Provider routes, SDK/model identities, policy choices, storage transactions, finance settlement, approval issuance, and artifact access still require their real owner agreements and implementations. The creative and DecisionPort schemas, C03 metering shape, and C04 handoff receipt remain local proposals until the external owner gate records and independently verifies the relevant agreements.

In particular, the locally pinned DecisionPort model identifier and synthetic provider names in the fixtures identify test inputs only. They do not establish an active provider route or live SDK compatibility. No live calls are made by the API test, build, or CI commands.

## Local checks and evidence

Use Node.js `22.23.3` for the production-target runtime checks. Node.js `24.15.0` is also tested for development compatibility. `make bootstrap` installs the root package and the locked TypeScript consumer tools. The strict public consumer test uses TypeScript `5.9.3` and imports the actual package subpaths.

```sh
make bootstrap
make build
make check TARGET=api MODE=mock
make check TARGET=brief MODE=mock
make check TARGET=inspection MODE=mock
make check TARGET=all MODE=mock
```

`make check TARGET=api MODE=mock` runs the API validators and writes a versioned, sanitized summary to `build/api-check-evidence.json`. `make check TARGET=brief MODE=mock` runs planner and API integration cases plus strict TypeScript consumer checks against the actual `api/v1`, `planning`, and `versions` package exports. `make check TARGET=concepts MODE=mock` runs the five local concept outcome families, their shared store and native-adapter regressions, strict v1.0/v1.1 TypeScript consumer checks, and a fresh offline tarball install whose installed public API creates two parentless siblings from two authorized references, replays without another dispatch, and rejects unsupported-version cases before dispatch; `MODE=CI` runs the same fixture suite, and `MODE=failclosedlive` emits a blocked report and exits 2 without reading credentials or contacting a provider. These checks use synthetic ports and intercepted transport; they make no paid provider calls.

`make check TARGET=inspection MODE=mock` runs the six CE-09 API acceptance cases, all seven inspection fixture buckets, storage and privacy tests, the populated V6-to-V10 migration and historical replay, codec integration, hard-exit/reopen behavior, and the strict `creative-engine/inspection` TypeScript consumer. It records the exact runner command and input hashes in `build/inspection-evidence.json` and TAP output in `build/inspection-test.tap`. `make check TARGET=inspection MODE=live` and `make acceptance TARGET=inspection` exit 2 with machine-readable blocked evidence until live target, authorization, Finance, usage mapping, event-sink, Q01, and host acceptance evidence is separately available. A mock pass does not establish that external approval.

`make acceptance TARGET=api` checks the same relevant canonical owner agreements as the creative contracts gate. `make acceptance TARGET=brief` emits machine-readable pending evidence and exits 2 until the package, asset-permission, invalidation-delivery, membership, and approval-staleness owner agreements have accepted pinned, independently verified artifacts. `make acceptance TARGET=inspection` additionally requires accepted DecisionPort, observer, metering, usage, Q01, and runtime-host evidence; local tests do not satisfy that gate. Current agreement status is in [canonical owner agreements](../contracts/canonical-owner-agreements.json).

The [public client example](../../examples/api/fail-closed-client.mjs) shows the unavailable response when a required scoped job port is not installed. The [strict API consumer fixture](../../examples/api/public-consumer.mts) compiles the existing v1.0 operations and new v1.1 concepts request, and checks read-only reservation and transport identities plus negative cross-version and caller-settlement cases. CE-02 adds a backend consumer fixture for its two brief operations and trusted planning/version ports through actual package exports.
