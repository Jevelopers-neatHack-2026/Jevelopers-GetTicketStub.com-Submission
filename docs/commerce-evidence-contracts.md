# Commerce, approval and evidence candidates: 0.4.0

Issues #22-28 provide ApprovalReference, ApprovalReceipt, ArtifactHandoffManifest, ProductionBundle, FulfillmentQuote, OrderAuthorization, FulfillmentStatus and EvaluationEvidence. ApprovalVerificationRequest/ApprovalVerificationOutcome and ArtifactConsumptionReceipt are separate proposals grounded in creative's pinned ApprovalVerificationRequest/ApprovalVerification/ConsumptionReceipt interfaces. They are not aliases for ApprovalReceipt; final naming and owner agreement remain pending. All canonical schemas are 2020-12, exactly version 1.0.0, with derived readonly declarations, standalone offline validators and individually indexed fixtures.

Use structural validateContract/parseContract, then checkCommerceEvidence or a narrow helper with separately obtained server expectations. The [installed consumer](../examples/commerce-evidence-consumer.mjs) uses independent synthetic scope and current records; [typed examples](../tests/commerce-evidence-types.ts) require injected contexts. Contexts are authenticated/current lookup results supplied by the owning application, print or supplier service. The library compares fields and hashes; it does not authenticate, sign, issue approvals, revoke records, render/preflight, create reservations, submit orders or update global evaluation state. No provider calls, purchases or publication happen here.

## Approval, verifier input and outcome

ApprovalReceipt binds application issuer, explicit audience/string actor, tenant/project, subject type and exact reference identity/revision/hash, intended use, exact preview, facts and optional composition references/hashes, assets, issue/expiry and status/policy references. ApprovalReference points to the exact receipt and binding hash. A boolean, URL/latest pointer, matching hash alone or consumption receipt is not authority. Current externally verified status must be valid; stale/revoked/unavailable/expired, forged issuer/audience/actor, changed subject/use/preview/facts/composition or transformed-byte reuse fails. References and audience are required in context; malformed context produces typed rejection.

ApprovalVerificationRequest carries the exact expected binding/audience and receipt reference. It can describe a request about a revoked receipt without granting use. ApprovalVerificationOutcome separately records valid/rejected/stale/expired/revoked/unavailable, exact request hash/reference, checked time and nullable verified binding. Its status must match the independently supplied current result; valid requires complete exact binding. No signature secrets, key service or verifier implementation is supplied.

## Source artwork handoff and consumption

ArtifactHandoffManifest explicitly requests source_artwork_production. Its approval binds the exact Artifact subject/revision/bytes and preview/facts for production use. A display-only design_preview approval is refused. This proposed owner-facing distinction is pending application/creative/print agreement and is separate from approval of the final composed production output.

The manifest binds design version/hash, artwork reference and exact metadata, preview, facts/composition/asset permissions, product specification and lineage. All declared identity/contract/revision values are checked along with hashes: same-hash wrong subject type, preview ID/revision, composition or facts cannot bypass binding. Exact source bytes are compared with separately supplied buffers. Access locator/policy/expiry and reauthorize_each_fetch are explicit opaque references, never bearer URLs or storage paths. Access expiry does not change artifact identity and never establishes permission. A handoff is not a finished print bundle.

ArtifactConsumptionReceipt binds the exact manifest/approval, consumer, idempotency, consumed byte set, access grants and consumption time. Exact duplicate receipt metadata remains the same observation; changed reuse of an idempotency key fails. It describes consumption only, never issuance of artwork approval or purchase authorization. The local creative ConsumptionReceipt remains a migration target with owner review pending.

## Production bundle and preflight

ProductionBundle records renderer/template/font/spec revisions, exact source-artwork/displayed-preview/facts/barcode/composition data, separately identified composed preview, complete output files/media/dimensions/units/hashes and preflight report/status/reasons. File sets and specifications must equal the trusted print result; supplied exact bytes must match every file's hash/size. Source artwork, displayed preview, composed preview and print output retain separate identities and hashes.

Preflight passed/failed/unsupported/unknown is explicit; presence of a bundle is not success. The semantic use helper refuses failed/unsupported/unknown preflight, missing outputs or inconsistent units. It verifies an independently supplied composition approval for the exact Composition and preview identity/revision/hash plus facts, not an unrelated source-artwork approval. Rendering, font rights, image decoding and actual preflight execution remain print-production work.

## Quotes and purchase authorization

FulfillmentQuote binds provider/quote/version, exact bundle/spec, product/variant/quantity/destination/shipping terms, currency, exact-decimal charge breakdown/total, issued/expiry, source observation and execution/billing mode. Unknown valuation retains null total; estimated and quoted are distinct from authorization/payment/settlement. Three-letter currency and declared precision are preserved. Pure BigInt digit comparison verifies quoted breakdown consistency, including discounts, without posting a ledger entry or converting currency. No customer address is in fixtures/evidence.

OrderAuthorization is application-issued purchase_only data bound to actor/audience/scope/internal order, exact current quote and bundle, maximum exact amount/currency, all purchase terms, issue/expiry/status and idempotency. The current externally authenticated authorization must match exactly, not merely cover a higher caller-selected ceiling. Changed quantity/product/variant/destination/shipping/bundle/currency/maximum or expired/revoked current records require renewed authorization. Quotes, budget holds, art approval and retryability cannot replace purchase authorization. No supplier submission or payment occurs.

## Fulfillment observations

FulfillmentStatus preserves supplier/internal-order/bundle/authorization/provider/attempt/idempotency/source-observation identity, effective time, normalized and opaque provider status, last-known state, submission outcome, cancellation and uncertainty. Unknown provider labels remain opaque and normalize only through a server-supplied mapping; absence maps to unknown. Timeout cannot become confirmed rejection/acceptance, and cancellation requested differs from supplier confirmation/rejection.

Exact same-revision records are duplicate observations, not another purchase or charge. Changed duplicates, stale/out-of-order callbacks, delayed progress regressions and terminal reversals fail. Under the same provider/billable execution, known supplier order identity and purchase-bound bundle/authorization cannot change. A genuine null-to-known supplier resolution must match separately supplied current mapping. Unknown outcomes do not release holds or trigger retries; storage/idempotency/reconciliation remain connector/finance work.

## Evaluation and public projection

EvaluationEvidence binds scenario/run/evidence and unchanged global acceptance IDs, exact component/contract/tool/source revisions, input/fixture hashes, provider/dependency mode, time/command results, measurements/units/baseline and sanitized artifact references. Claims are contribution_only; there is no global_verified state. Planned/passed/failed/blocked/unmeasured/unknown remain distinct. Unmeasured/unknown metrics have null values, never zero. Passed requires observed command success, measurements, known mode and finish time; actual records must equal independently supplied execution expectations. Baseline deltas require a bound baseline reference.

Closed nested fields, safe identifiers, controlled invocation/limitation vocabulary and opaque references exclude credentials, auth headers, raw prompts/source/customer data and signed URLs. projectEvaluationEvidence emits the existing allowlisted EvidenceProjection shape only: separate opaque evidence ID, modes, outcome and integration-evals component revision. It excludes private refs, measurements, hashes, customer data and diagnostics. Schema/fixture passes cannot change global authentication/finance/production/live-provider status; integration-evals owns that state and actual evidence review.

## Hashing and compatibility

commerceContentHash computes canonical JSON/UTF-8 SHA-256, excluding only the named self-hash field. ArtifactHandoffManifest additionally excludes access.locator_ref and access.expires_at as mutable access descriptors while retaining access policy and renewal rule. All delivery/scope/domain/version/approval/purchase/production data otherwise remains bound; validation never rewrites hashes or money. Hash equality does not authenticate an issuer or permission. Exact byte hashing differs from manifest hashing.

Pinned foundation/operations/research schema bytes and runtime semantics stay unchanged. The new profiles are candidates, not accepted migrations of creative.approval-handoff.proposal/v1. Source evidence: [creative interface](https://github.com/Jevelopers-neatHack-2026/creative-engine/blob/4e28839ea8baeb4112a4f12340ef2fe84f5c8efe/src/contracts/approval-handoff.d.mts). Production/fulfillment/evaluation source pins remain documentation baselines; no local substitute is actual integration. Full local schema/fixture/compatibility coverage now exists, while --require-owner, --require-consumer-pins and contracts:consumers remain blocked by genuine missing external evidence. Final release/harness work is the next assigned group.
